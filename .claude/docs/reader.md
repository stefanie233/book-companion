**结论**：reader/js/ 14 模块

### 76. 跳转与恢复的优先级

**结论**：显式跳转（笔记页/浮窗批注、图谱节点「跳转原文」）统一走 `app.js jumpToPosition()`：`switchTab('reader', true)` + 自己驱动切书 + `invalidatePendingRestore()` + `whenHostVisible()`

**理由**：恢复类定位**都是延迟执行**的（`restoreViewport` 等布局稳定 ≥2 帧、`_armLateVerify` 等补载静默 ~2s）。旧实现把跳转写在 `switchTab('reader')` 之后，它们全部晚于跳转落地把视口拉回 —— 实测视口停在原处、sync 却已记下批注那一章（"点了没反应"）。另：切 tab 后**同一 tick 里阅读区仍是 0×0**，此刻定位落在零尺寸舞台上

### 77. display 的完成信号

**结论**：定位链里 `rendition.display()` 一律走 `_displayWithTimeout()`（2.5s 有界等待），**不裸 await**；跳转落点另用 section 基**核验**、未到位重试

**理由**：fork 的 display promise 会**永不 resolve**：实测切 tab 后从笔记页跳转，目标 section 已渲染、scroller 已移到位，promise 8s 不返回。裸 await 卡死整条定位链（45s 后 `jumpToAnchor` 仍未 settle，之后每次跳转都挂在 `_restoreChain` 上）。而 display 之后的收敛循环本就按几何读回校验落点，不依赖该 promise

### 78. 视口指纹跨块

**结论**：`match_page_text` 的命中判据加一级**跨块拼接**（单块包含 miss 后按章拼接、定位偏移、映射回块）

**理由**：视口顶文本横跨相邻两块是**常态**：`jumpToAnchor` 刻意把目标块首对齐到视口顶（留 24px 边距），顶行天然是「上一块的尾巴 + 这一块的开头」。旧判据恒 miss → 跳转落点被判"未命中" → 示数不回刷、进度不落库，退回跳转前的旧章（实测参考书Ach20 ck5：指纹 = ck4 尾「…5月27日」+ ck5 首「为何要欺骗自己呢？…」，两侧都不含整串）

### 79. 图谱节点跳转

**结论**：节点详情面板「跳转原文」→ `jumpToPosition(bookId, chapter, chunk)`；`get_full_graph` 的节点带 `chunk`（first_appearance join graph_chunks 现算）

**理由**：章号是导出量、段落才是落点（只给章号会停在章首）；与批注跳转共用同一入口，切 tab / 切书 / 作废恢复 / 等可见四件事只写一处

### 80. 分支切换与上下文一致

**结论**：分叉点渲染 `‹ n/N ›`，切换 = `loadSession(兄弟会话)` 整会话替换；`get_branches` 必须带 **siblings**（同父同 fork 点）；**锚点 = fork 发生的那条消息**（重新输入→用户气泡，重新回复→agent 气泡；旧 NULL 行逐消息比对推断）；**恢复视图取族谱内 `time_updated` 最大的一支**；**后端以 `session_id` 回读会话重建 history**，前端快照只在新会话无 id 时兜底；前端 `S.chatEpoch` 作废在途流的后续写入

**理由**：分支树是按「父 + 当前」组织的，只查 children 拿不到同父兄弟；而上下文曾完全信任前端 `history` 快照 —— 界面在 B、请求发 A 的窗口真实存在（快速切换 + 在途打字机/错误兜底仍会 push）。视图可以切换得比请求快，但**写入目标与会话上下文只能有一个真相源**；`fork_point_index` 曾因 INSERT 漏列全部落成 NULL，导致整条分支链不可见 —— 索引与「从哪分叉」必须显式持久化

### 82. 阅读位置真相源

**结论**：`/api/sync` 同时收 **topSection + pageText（恢复锚）**、**focusSection + focusText（阅读意图，视口面积最大的 section）**、**visibleSections（门的上界）**；`sectionIndex → book_chapters.spine_index → chapter_index` **结构定章**，文本指纹只在该章内**定块**；**无 spine 映射时也优先用 focusText 匹配**（比视口顶尾巴更接近阅读意图）；`match_page_text` 的 hint 覆盖只留给无结构坐标的旧客户端；选区坐标（native section / chunk-mode chapter+chunk / FTS 兜底）+ **选区锚文本（±上下文，用于同名短词消歧）** 是「已见」证据，`spoiler_gate = max(阅读章, 可见章, 选区章)`，`<selection-context>` 锚到选区块

**理由**：旧链路把「视口顶第一个字」一个拟合值同时用于恢复锚、阅读进度、剧透门：章节边界上视口顶仍是上一章尾巴，指纹命中上一章，`hint` 再把下一次上报钉在同一章（自锁）—— 实测屏幕在二十四章、门卡在二十三章，模型侦察两轮才回答。`_find_chunk_by_fp` 的跨块拼接只在同章内，跨不了章；渲染层本来就有 `sectionIndex`/CFI 结构坐标，不需要「捕获屏幕所有文字」，只需要把三个问题分开回答。`spine_index` 有 4 本旧书全为 -1，且存在一章多章共存，故结构路径必须有指纹兜底；选区只给一个短词（「杨修」）会命中本章第一块而不是读者真正选的那块，锚文本把上下文一起带上

### 84. 会话按页签分线（主页 / 阅读页 / 写作页）

**结论**：三条独立会话线，指针存 `localStorage.bc_tab_sessions`（`{id, day, bookId?}`），切页只恢复**本日**的线（没有就开全新会话界面）；换书（从书架打开另一本 / 阅读页切书）清掉阅读线并开新会话。`/api/chat` 带 `page`（home/reader/writing），后端按「mode + project_id」判定会话归属：跨线 `session_id` 一律当新会话且丢弃客户端历史快照。主页请求清空阅读现场（book_id / 选区 / 进度 / 剧透门），只注入 `<home-context>`；扮演按首页线，保留书与角色卡。会话导航栏打开时按当前页预选二级页签（主页 → 全部 / 阅读页 → 按书籍 / 写作页 → 写作），只预选不锁定、顺序不变；重命名保留悬停铅笔按钮，但提示文案改成「快速双击进行重命名」，「重命名」字样不再出现（双击标题同样可改名）。

**理由**：三个界面的提示词本来就不同（home-context / reading-context / writing prompt），旧实现主页与阅读页共用一条线，且 `S.currentBook` 残留会让主页请求带上 reading-context —— 历史、标题、mode 全跟着错页。`day` 用本地日期而非会话 `time_updated`，表达的是「这条线今天用过没有」；否则隔天打开会把昨天的对话原样搬进今天。前端指针 + 后端归属校验是双保险：旧标签页、旧缓存或直接调 API 也不能把别页的 `session_id` 续写进来。

### 85. 空会话预选阅读模式 + 新会话置顶 + 导入归书架

**结论**：阅读模式是三档分段药丸（沉浸伴读 / 俯瞰分析 / 发散探索），只在**阅读页的空白会话**里浮在聊天框中央（主页 / 写作页不出现）；发出第一条消息后整块消失，该会话的模式就此冻结、界面不再提供改模式的入口。面板拖窄到放不下标签时（容器查询 320px，锚在 `.chat-body`）退化成纯图标，名字留在 `title`。选中块是一枚独立浮动的药丸，切档时整块滑过去：位移 + 挤压/拉伸走 WAAPI（约 460ms，弹簧缓动、中途 12% 以内的形变、收尾轻微过冲），快速连点从当前形变处接着走；`prefers-reduced-motion` 下直接落位。托盘（输入框上方按钮行）第一位固定是「新会话」，主页 / 阅读页 / 写作页都在。「导入书籍」从托盘移出，放到书架页「全部藏书」标题旁，只在书架出现。

**理由**：模式原来藏在阅读页的下拉里——会话开始前看不到选项，主页也没有入口。模式是**会话级**属性（换一种读法等于换一套上下文），所以放在会话开始前、跟空聊天框待在一起：第一条消息一发出就撤掉，避免中途改模式把同一段历史读成两种口径。判断「空会话」用前端状态（无 history 且无 session_id，会话懒创建）而不是 DOM 文本。导入是书库级动作，跟着书架标题走才符合归属；托盘留「新会话」这个三页都成立的动作。窄面板退化用容器查询而不是视口断点：聊天面板宽度由 splitter 决定，和窗口宽度无关。

### 86. 阅读页默认书 = 「继续阅读」真相源

**结论**：进入阅读页（点侧栏「阅读」、或刷新恢复）时，若内存里没有当前书，默认打开**书架「继续阅读」卡片那本书**（`pickContinueBook()`：`max(last_read_at, last_opened_at)` 最大者，`/api/books` 同一份数据），**不是**下拉框第一项；且 `bc_view` 必须在**选书完成之后**落盘（`refreshBooks()` 里 `await selectBook()` 再 `saveViewState()`），`restoreViewState()` 遇到 `{activeTab:'reader', bookId:null}` 也要恢复阅读页并交给 `refreshBooks()` 挑书，不得退回书架页。

**理由**：`/api/books` 的顺序是 `time_updated DESC`，与"读到哪"无关（实测第一项恒为《卡拉马佐夫兄弟》）。旧链路三处叠加：`refreshBooks` 不设默认值 → `<select>` 停在第 1 项；`switchTab` 末尾的 `saveViewState` 早于异步选书 → `bc_view` 记成 `bookId:null`；`restoreViewState` 只认 `reader && bookId` → 刷新退回书架。现象因此是"继续阅读卡片写《房思琪》，点开阅读页却是《卡拉马佐夫兄弟》，再刷新直接掉回书架"。书架卡片与阅读页各算一套"上次读的是哪本"必然漂移，两处只能共用 `pickContinueBook()`。全新书库（无任何时间戳）宁可空着，也不要按排序副作用替用户选书。

### 118. 写作页版本图（泳道）

**结论**：写作页「版本」面板的历史列表改成 `git log --graph` 式泳道图。按时间倒序一行一条提交，每列记着「这一列接下来在等哪条提交」：一条提交到来时，凡是在等它的列都接到节点（最左那列留下继续往下走，其余列画圆弧汇入），随后第一父节点接管本列、第二父节点（合并）另起一列；父提交不在可见窗口就断线，不补假线。历史默认带 `all=1`（图谱要看得见岔路）；「只看本章」从**过滤**改成**置灰**——`vcs_log(mark_chapter=True)` 给每条提交带 `touches` 布尔，整页用一棵 `tree_json` 只解析一遍的缓存算完。行高 44px 是三方常量：`writing.js` 的 `GRAPH_ROW_H`、CSS 的 `--graph-row-h`、实际行高必须相等。

**提交可展开（VS Code 式提交明细）**：点一条提交行 = 展开/收起它相对第一父节点的改动清单——章在前（按章序）、工作区文件在后（按路径），每行末尾是中文状态「新增 / 修改 / 删除」；点清单里的章或文件，中间栏只渲染这一份的逐行差异（复用 `openVcsDiff`，`isFile` 时隐藏章级回滚/撤销/摘取按钮）；账本不是一份文件，单独一行「账本」（只有新增/只有删除才标「新增/删除」，混着就是「修改」），点开走整条提交的 diff。不再放「查看全部改动」——展开清单已经把章和工作区文件都列全了，那一行只是重复。清单按需取 `/vcs/diff?from=<父>&to=<提交>&text=0`，结果按提交 id 缓存（提交内容不会变），展开状态存 `S.vcsExpand`、换作品时清空。展开块是提交行的兄弟节点而不是子节点，否则点文件会被当成再点一次提交。展开块左侧的泳道续线按「本行之后仍活着的列」画满整个清单高度：`layoutCommitGraph` 每行多带一个 `after`（画完后的 lanes），高度 = `GRAPH_FILE_PAD_Y` + 行数 × `GRAPH_FILE_ROW_H`，这两个常量必须与 CSS 的 `.write-graph-files-body` 内边距、`.write-graph-file` 行高相等，否则下一行的竖线会从半空中开始。展开是 180ms 的高度动画（`--files-h` 由 JS 按行数算好，`S.vcsOpening` 保证只在清单真正出现的那一帧播一次，`prefers-reduced-motion` 下关闭）；收起保持即时——点击已经表达了意图，收的过程再拖 180ms 只会挡住下一条提交。

**理由**：整条父子链是图的骨架，按章过滤删掉中间节点会把泳道画断，读者分不清「线本来就断」还是「被筛掉了」。颜色按**列**取而不是按分支取：同一列在时间上就是同一根线，换列才换色，这正是 git 图的读法；分支身份交给节点旁的引用胶囊（分支 / 标签 / 当前分支染强调底色）。同一行里「合并进来的列」与「第二父节点新开的列」可能落在同一列，判断竖线是否贯穿必须比前后的**值**而不是非空——否则会多画一根线，看起来像一个分支穿过了合并点。

### 119. 写作页只做「写」，装配交给 harness

**结论**：顶部动作排只保留文档级操作（撤销 / 重做 / 还原 / 暂存 / 保存 / 生成正文）。「合同」「上下文」「结算」三个按钮从页面移除，侧栏也只剩「审稿」「版本」两页；这三件事统一由写作页右侧的写作 harness 承担（`writing_create_chapter` / `writing_set_contract` / `writing_draft_chapter` / `writing_settle_chapter`）。风格诊断改从生成流的 `stage: assembled` 事件回填，不再为看诊断单独装配一次上下文。会话托盘上的「写作助手」装饰标签（无点击行为）一并删除。合同仍是硬边界：无合同点生成只提示去找写作助手，页面不再提供手写合同的入口。

**理由**：三个按钮是同一能力的第二条「手装配」路径，参数比 agent 工具更少，状态也更容易漂移。结算那条尤其糟：`handle_writing_settle` 的 422 body 是 `errors` 数组而非 `error` 字段，页面 `api()` 取不到原因，用户只看到「请求失败 (422)」，而 harness 工具会把拒绝原因逐条转述。留着 UI 会诱导用户绕过 harness，让写作页同时维护两套流程；删掉后写作页只回答「这一章写得怎么样、改过哪些版本」，流程判断回到同一个 agent。

### 122. 引用的出处跟页面走（阅读页 / 写作页）

**结论**：引用条只有一个（`#selectionTag`），但出处分两套：阅读页是「书中原文 / 对话」，写作页是「正文 / 工作区文件（夹） / 对话」。正文引用来自 `<textarea id="writeEditor">` 的 `selectionStart/End`——`window.getSelection()` 拿不到 textarea 内部的选区，所以由 `writing.js` 读选区、调 `chat.js` 的 `setWritingSelection()` 写入；**发送前复核锚点还在不在编辑器里**（`editor.value.includes()`），不在就当场丢掉并提示一句；换章时收起写作页的引用。前端只发与当前页面同源的引用（阅读页的书里原文不进写作页，反之亦然）。后端在 `mode=writing` 时只认 `selection_source ∈ {writing, workspace, chat}`，其余一律丢弃，注入走 `writing_selection_block()`：正文块上限 **1200 字**（阅读页是 200），并明说这段已随本轮落盘、可直接当 `writing_replace_text` 的 `anchor_quote`；`workspace` 块只给**路径**（文件夹以 `/` 结尾），明说先 `writing_docs(action="read")`（文件夹先 `list`）再动手（决策 135）。

**写作页的引用 = 编辑器里的选区，两者同生同灭**：拖选松手即出引用条，并把光标送进聊天框（可以直接打字）；取消只有一个真相——**选区没了，引用就没了**。焦点一走 textarea 就不再画选区（Chrome 直接不画，`::selection` 也救不了），所以引用期间另挂一层 `position: fixed` 的镜像 `.write-veil`：文字透明、字体/行高/内边距/可用宽度照抄 textarea，换行逐字对齐，只在 `<mark>` 上涂半透明底色；编辑器重新获得焦点、清引用、切视图时撤掉，`ResizeObserver` + `scroll` 负责重排。触发取消的有三条路：点 ×（走 `mousedown` 而不是 `click`，触发面积约 1.5×）、在正文里点到选中段以外（选区塌陷）、点写作台内正文以外的区域或导航栏。点聊天面板和写作台以外的地方**不**取消（光标得待在那边才谈得上引用）。`select` 事件只更新引用条、**不动焦点**——拖选过程中它连续触发，抢焦点会让人选不完整；焦点只在 `mouseup` 时转移。

**阅读页同理，但用另一套高亮机制**：书页里选中即出引用条（`source=书中`）并用 **CSS Custom Highlight**（`::highlight(reader-quote)`）把选区单独标出来——它跟 DOM 选区互不依赖，点进聊天框、浏览器把选区收缩之后底色还在；取消渠道：点书页别处（选区塌陷）、换页（`loadChunk`）、换书、点导航栏，点聊天面板不取消。阅读页**不**自动把光标送进聊天框：选中一段再 Ctrl+C 是阅读里的常用动作，抢焦点会把它废掉。

**交互页的「对话引用」只认气泡里的文字**：`#chatLog` 下除了消息气泡，还挂开场招呼语（`.msg.agent` 直接放文字、没有 `.bubble`）、时间戳与会话提示条。它们不是一轮对话的正文，原先「`#chatLog` 内任意选区都算引用」会让误触的一句「这么晚还在……」变成引文带进下一轮。现在选区的起止两端必须落在**同一个 `.bubble`** 内（跨气泡拖选也不算一条引用）；非气泡文字不改动已有引用。取消引用还有一个只在「选区还活着」时出现的坑：点 × 的 mousedown 一摘 `.visible` 标签就从布局里消失，mouseup 往往落在它下面的元素上，而 `preventDefault()` 又刻意留着那段选区——mouseup 钩子会按同一段选区把刚撤掉的引用原地装回去，看起来就是「选中文字时点 × 没反应」。现在 × 的 mousedown 先打一个一次性的指针标记，紧随的 mouseup 直接跳过；下一次不落在 `#selectionTag` 上的 mousedown 会清掉标记，真正的新选区不受影响。

**理由**：`mode=writing` 原本把 `selection` 一刀切清空（阅读上下文整体不进写作轮），但引用不是阅读上下文——它是作者指给 agent 看的那几行。之所以还要复核，是因为编辑器里圈选和删除共用同一个动作：圈完又改过的段落锚点已经不在正文里，带上去只会让模型在正文里瞎搜；机械复核比「一改动就清空引用条」更准（改别处不该让引用失效）。正文在发送前已 flush 落盘（`WritingUI.flush()`），所以引用天然对齐工具读到的那份正文。截断放宽到 1200 字，是因为写作圈选常常就是一整段，按阅读页的 200 字会把要改的那段从中间切开，`anchor_quote` 直接失效。

交互上踩过的坑：× 用 `click` 时**第一次点不动**（按下与松开之间编辑器失焦，这一下整个落空，要现在别处空点一次才好使），改 `mousedown` + `preventDefault()` 后稳定；图标按钮原先的可点区只有 22×14，点不中就等于没有撤销渠道；引文原本用 `--hl-gold` 上色，在淡金底上等于隐形——金色只留给图标、边框和底色，字用 `--text-strong`。

### 125. 写作台左栏是两个导航：作品与版本控制

**结论**：写作台左栏只有两个导航：**作品**（项目浏览器，标签就是当前书名）与**版本控制**（VS Code 的 Source Control）。左栏顶部第一行是独立的**切换作品**下拉（与「新建作品」同高）——书名 tab 只负责切到项目浏览器，换书走这一行，两个职责不叠在同一个按钮上。作品视图是一棵树，根下两个文件夹：

- `正文/`：作品 → 卷 → 章 → 场景，全部章节都在（状态只做行尾圆点）；章行右侧再挂一枚方形合同徽章（缺合同 / 有合同 / 已结清）。`正文/` 行右侧有「合同总览」与「新建章节」。
- `工作区/`：作品记忆、设定、计划稿、素材（见决策 126），点文件在主区只读渲染。

**合同不是树里的第三个文件夹**：它是章节的派生投影，做成文件夹会让同一批章出现两次；整本审阅走 `正文/` 行的「合同总览」，按章看就在章详情里。**版本控制**是左栏的另一种模式，照 VS Code 的「源代码管理」排：提交盒（分支下拉 + 提交说明 + 提交/修正 + 暂存/标签/找回）在最上面，下面全是可折叠分组——更改 / 图表 / 分支 / 标签 / 暂存 / 位置记录 / 反馈，只有「更改」「图表」默认摊开，开合状态记在 `localStorage.bc.writeVcsGroups`。**版本图（泳道）也在这块面板里，不进主区**；点一处改动或一条提交才由 diff 覆盖层接管。切到版本控制时树让位（`display:none`），面板自己滚，**主区不动**——还是原来那一章，头部与风格条照常在；右侧面板只剩审稿；头部分支徽章仍是版本控制的第二入口。合同总览仍走 `GET /api/writing/works/{id}/contracts`，卡片列出目的/独占事件/章末状态/下场可承接/故事时间 + 必须兑现/必须保留/禁止触碰，点卡片跳回正文那一章。

**理由**：四个平级药丸把「项目里的东西」（正文、设定、合同）摆成了「四种模式」，跟 VS Code 的心智模型相反——Explorer 和 Source Control 是两个**视图**，项目里的东西是同一棵树里的节点。合成一棵树后，更多东西（素材、以后的工作区文件）只是多一个文件夹，不再多一个药丸。**合同不做文件夹**：它不是独立文件，而是章节的派生投影；做成文件夹后同一批章出现两次，改章/删章要同步两处，作者会分不清本体。**选中节点 ≠ 当前写作章**：点「设定/人物A.md」只切主区，不能改 `S.chapter` / `writing_chapter_index`，只有点正文里的章才切当前章——否则下一句「生成正文」会写到错章。头部（章标题、撤销、保存、生成正文）与风格条按**视图**判断（`TEXT_VIEWS`）而不是按导航：版本控制停在左栏时，主区还是正文。**版本控制不能占写作区**：写作区是写正文的地方，版本图、提交盒、分支列表都是导航与状态，跟 VS Code 的源代码管理一样属于侧栏；判断依据不是「有多少内容要放」，而是「查一眼历史要不要离开正文」。审稿原来只有「对照检查」这一条小路能打开，所以补了头部一枚「审稿」按钮。合同只做收录不做表单：合同是硬边界，写合同的入口留在 harness（决策 119），页面再开一套手写表单只会让两处状态漂移。

### 126. 草稿是作品工作区（作品记忆 / 设定 / 计划稿 / 素材）

**结论**：写作台「草稿」分区是这本书的**工作区**，放在 `data/writing/works/<work_id>/`，是四块普通 Markdown 文件，和正文一起进写作 git（决策 127）：

- `作品记忆.md`：这本书是什么、写作约定与忌讳。**只放低频层**——现在到哪、下一章往哪走由账本与合同提供，不在这里复述（决策 129 的单一归属）。system prompt 里**全文**带上（上限 3000 字，超长截断并显式标记），写作上下文的 `work_docs` 块里再带 2000 字。
- `设定/**` 设定：人物 / 世界观 / 事件 / 地点 / 术语，一个主题一份。作者心里的 demo 经交谈后现形的沉淀物（决策 131）。system prompt 只带**索引**（路径 + 字节 + 首行），要正文由模型调 `writing_docs(action="read")`；写稿时整块带上正文（`work_docs` 块：可选、priority 85、1400 tokens、`degrade`——装不下先裁后丢，合同与账本永远不动）。
- `计划稿/**`：结局备选、章节设计、结构实验。**任何上下文都不自动带**，作者要看才读；三条去向与弧线指针见决策 132。
- `素材/**`：项目外的上下文——书外的观察、例子、语料、别的作品里的写法与物象。**不自动召回**，由作者和 agent 一起翻、找出可以并进这本书的合并项（决策 130）。

目录名面向作者：用「设定 / 计划稿 / 素材」，不用 `docs/`、`plans/` 这类英文技术词；`.md` 只是文件的真实后缀，页面上（目录树、主区标题、版本面板）一律显示去掉后缀的名字——创作者不需要知道文件格式。旧工作区里的 `docs/`、`plans/`、`试错稿/` 在 `ensure_workspace` 里顺手并进新目录，同名文件留在旧目录不覆盖。三个目录即使为空也由目录接口列出来（`list_dirs`），左栏始终有「设定」「计划稿」「素材」三块占位；建作品时 `ensure_workspace` 就建好它们，不必等第一份文件。

写入只认这四处、只收 `.md`：逐段校验（禁 `..`、绝对路径、盘符、隐藏文件、控制字符）+ `resolve()` 后必须仍在作品目录里；作品记忆不能删（要清空就写空）。agent 工具 `writing_docs`（list / read / write / append / delete）归写作助手；页面只做**文件管理**（新建空文件 / 改名 / 删除，决策 135），正文内容仍只由助手写——编辑入口不开第二套（与决策 119 同一条理由：同一份东西两个写者，谁覆盖谁说不清）。删除作品时工作区目录一起删。HTTP：`GET /api/writing/works/{id}/docs`（目录）与 `.../docs/file?path=`（正文；接口路径是内部协议，不随显示名改）。

**理由**：**文件而不是库表**——作者能用任何编辑器打开、备份、丢进自己的 git。**四种口径而不是一把梭**：作品记忆是短总纲，全文带上最省事；设定会长到几十份，全文注入会挤掉合同与账本，所以只带索引、按需读；计划稿是试错，素材是库存，两者进了上下文都只会污染判断，所以都不自动带——但检索形状不同（计划整篇翻，素材找合并项），所以不共用一个目录。**预算照旧走 `compile_blocks`**：新块必须先定失败语义，`work_docs` 是可选 / degrade，挤掉它也不许动正典。外部 agent 说明文件的加载也是这套：有上限、有分隔、超长显式截断——我们只是把「项目说明」换成了「一本书的说明」。

### 127. 作品工作区进写作 git

**结论**：提交图不只存正文与账本，也存工作区文件。`commits.files_hash` 是这条提交的「路径 → 内容 hash」清单指纹（v8 迁移；空串 = 旧提交，未跟踪）；`commit_files` 存清单，正文按 hash 落在 `work_file_blobs`（同一份内容在多次提交间只存一份）。`vcs_status` 多报 `file_changes` / `file_counts` / `files_dirty`，有未提交的设定也算「不干净」；正常提交把当前工作区文件一起带上，「只提交几章」沿用 HEAD 的清单；回滚 / 切分支 / 合并 / 撤销 / 摘取 / 暂存回放都把文件写回磁盘（多出的文件删掉），三路合并在文件级同样能自动合、撞了报 `kind=file` 冲突交给裁决（`resolutions` 键是 `file:<路径>`）。版本面板的「更改」分组把文件改动排在章节之后，点一条打开草稿区的原文。

**理由**：设定和正文是同一本书的两个部分。之前把工作区排除在版本之外，回滚到「第三章定稿」时人物设定却停在今天，历史是半截的；作者在版本面板里也看不到自己刚改的作品记忆，只能靠提交说明记。hash 清单让状态比较只读一次目录，正文按内容去重，重复的 checkpoint 不会把同一份设定存很多遍。旧提交没有清单，回放时一律不动磁盘——宁可少做事，也不能拿空清单清掉作者的工作区。

### 128. 合同是验收单，写前是边界、写后逐条勾

**结论**：`chapter_contracts` 增加兑现生命周期（v9）：`status`（`active` 在写/待写、`closed` 已结算）、`closed_at`、`outcomes`（`[{item, verdict, evidence}]`，verdict ∈ hit / partial / miss）、`close_note`。**没有作者批准环节**：agent 写完合同即可动笔，作者事后可改；**改合同 = 重新立约**，`set_contract` 把状态推回 `active` 并作废旧兑现记录。**一章一约**，不拆场次合同。结算（`writing_settle_chapter`）成功即结清：`outcomes` 由 agent 逐条申报（每行 `hit|条目原文|逐字证据`，没做到写 `miss|条目|原因`），宿主只存不判；未申报的条目在盘点里单列，不算兑现。注入按状态分档：`active` 全文进 system prompt；`closed` 只留一行「第N章合同已结清｜兑现 x/y｜未兑现 …」；写稿上下文的 `chapter_contract` 必需块不受影响。上一章结清时 `miss` / `partial` / 未申报的条目，作为「上一章合同未兑现」出现在下一章的现场里，去处只有两个：写进下一章合同，或转成承诺。

**理由**：合同原本只做了「写之前」那一半——它挡住没合同的生成，却没有任何东西核对写完之后每条必须兑现有没有发生，`must_hit_now` 等于一份没人签收的验收单。把它做成有状态的东西，才能同时解决三个问题：**注入生命周期**（写完了的合同不该继续占着每回合的提示词，现在从约 700 字降到一行）、**兑现留痕**（合同页能看到逐条勾选与结清备注）、**欠账承接**（未兑现项不会随章节结算一起消失，下一章的合同或账本当载体）。作者评审环节刻意不做：文学不需要签字，agent 的默认权 + 作者的否决权比每章等一句确认更顺手；这也是「指令遵循已经很好」的前提下的取舍。校验口径（证据是否真在正文里、LLM 复核）留到后续，当前只保证「申报了、有记录、能追溯」。

### 129. 写作工作区的四条不变量

**结论**：工作区分几块可以改，但这四条不能破，任何新模块都要满足：

1. **单一归属**——一个事实只有一个权威家。硬事实（生死、在场、知晓、物品位置、关系状态）归账本；纹理（说话方式、外貌质感、习惯）与不可推导的意图归设定；可推导的（年表、关系图、进度、谁在哪）不落文件，现算。
2. **变化频率定位置**——越低频越靠前。作品记忆（规则）在缓存前缀里，设定索引居中，合同 / 账本 / 上一章尾 / 版本现场在尾部或 user message；历史（git log、旧章节）永不常驻，只可查。
3. **发现与检索分离**——索引回答「有哪几个分区、大概多少」，检索回答「具体是哪一条」。索引有上限就必须显式报「还有 N 份未列出」，不许静默截断；`writing_docs` 要有 `search`，否则「按需读」退化成猜文件名。
4. **可推导的不手写**——能从账本和正文算出来的视图一律生成，不落成文件。

**理由**：四条都是被同一个失败模式逼出来的——模型不是「选择性失明」，是**真的不知道有**。现在 `index_lines` 是 `limit=40` + 路径排序，第 41 份起静默消失，而且哪 40 份出现由首字排序决定；`writing_docs` 只有 list / read / write / append / delete，读到哪份全靠猜。规模一上来，设定和素材都会变成「存在但不可发现」。项目自己在预算层立了「宁可失败不可静默丢正典」（`ProtectedContextOverflow`），索引却违背它。同理，不把整个目录树注入上下文，而靠 agent 自己检索——我们缺的正是这只手。

**落点**：`docs.overview()` 出分区索引（设定 20 / 素材 12 按修改时间 / 计划稿 20，各带未列出计数）；`writing_docs` 加 `search`（scope + 返回首行与命中片段）。

### 130. 素材库是项目外上下文的合并项

**结论**：工作区第四个根 `素材/`，与设定、计划稿同级，进写作 git。定位是**项目外的上下文**：书外的观察、例子、语料、别的作品里的写法与物象。它**不自动召回、不进常驻上下文**，只给清单；由作者和 agent 一起翻，找出可以并进这本书的**合并项**——合并动作落在设定或正文，素材原件留在库里不退场（它本来就不是这本书的一部分）。

跨书读取：默认只认本书；用户点名才允许只读别书，且**只认 `素材/`**，不许读别书的 `设定/` 和 `作品记忆.md`（别人的正典与剧透不该进来）。命中内容进 `external_reference` 块——该块的语义本来就是「别本书的素材，比本书历史段落更远一层，永远先丢」。

**理由**：素材与计划共享的只有「不进上下文」一个属性，职能不同——计划是意图、消耗品（执行完可归档），素材是库存（越攒越值钱），清理规则不同，不能共用一个抽屉。更关键的是我们**不做全自动写作机**：素材的价值恰恰在于作者和 agent 一起挑，自动召回会把它变成噪声源，还会把同一段素材反复塞进每章。跨库只开只读、只限素材，是防止「借写法」悄悄变成「搬正典」。

**落点**：`ALLOWED_ROOTS` / `list_dirs` / `_iter_files` 加 `素材`；跨库读取走 `writing_docs(action="read"/"search", work_id=...)`，只读、范围锁死 `素材/`、且不改当前现场；`writing_docs` 的 `search` 覆盖素材。`external_reference` 仍是**自动召回**（参考书）的落点；显式读到的跨库素材留在会话里，不进草案预算块。

### 131. 设定是作者 demo 的现形

**结论**：`设定/` 不是外面灌进来的规格书，是作者心里那个 demo 经过交谈之后**现形**的沉淀物——对话里说清楚一件事，才算落地一份设定。因此设定由 agent 在交谈后写，不导入、不自动抽取。与账本的分工按**域**切，不按**优先级**切：**硬事实只进账本，设定只收纹理和不可推导的意图**；不再用「冲突时以账本为准」这种优先级规则兜底。

**理由**：优先级规则要求模型每回合自己判断「这里冲突了、该听谁」，而模型没有可靠的冲突检测能力，实际表现是两边都写进去或随机挑一边。工程里 docs 与 code 是域分离——code 是真相、docs 是说明，没人写「冲突时以 code 为准」，因为两者根本不描述同一层。设定与账本同理。**现形**这个定位还定了两件事：设定要能追溯到是哪次交谈定下来的（写作 git 的提交说明是载体）；不允许出现「没人说过、agent 自己补全」的设定——补全的只能进计划稿，等作者确认。

### 132. 计划的三条去向与弧线指针

**结论**：计划稿只有三种去向，且都要显式发生：

1. **落地** → 在计划稿顶部注一行「已并入 设定/xxx」，正文不复制——同一份设计只允许一个权威家（不变量 1）。
2. **废弃** → 标「已废弃」+ 一行原因，不删。
3. **仍悬着** → 弧段边界做一次对账：逐条走计划稿，标已落地 / 已废弃 / 已改。由结算或弧段切换触发，不靠自觉。

另外「当前弧」要有显式指针：合同顶部带一行 `弧线: 计划稿/第二卷/第12-20章.md`（引用，不内联），draft 需要方向时一次读。

**理由**：合同校验的单位是章，不是计划；计划改了合同不回溯，正文又可能和两者都不一致——三方漂移没有对账就会在几十章后分叉。弧线指针回答「我在哪、接下去往哪」，必须显式注入，不能指望模型从账本里推导出来。作品记忆瘦身之后，这是上下文里唯一还能回答「这一卷往哪走」的地方。指针用引用不用内联，是因为计划稿会改，内联的副本一定会过期。

**落点**：`chapter_contracts.arc_ref`（v10）+ `writing_set_contract` 的 `arc_ref` 参数；`_contract_text` 渲染成「弧线：…」，合同页同步显示。

### 133. 项目记忆维护走两段式

**结论**：写作记忆不在对话里顺手写，而是分「抽取 → 合并」两段：

1. **抽取（Phase 1）**：每章结算后，看正文 + 合同 + 结算 + 作者原话，抽成结构化候选（preferences / settings / plans / materials），先落 `work_memory_log`。没有值得记的就 `no_op`，不产生待办。
2. **合并（Phase 2）**：读待办 + 当前 `作品记忆.md` 与 `设定/` 全文 + 作者自上次合并以来的文件增删改，产出一组 ops（整份 bible 替换、设定写入、设定删除）。机械闸门判过才落盘：只写 `作品记忆.md` 与 `设定/`，记忆 3000 字上限，单文件 64KB，最多 200 份；判不过整批拒绝并带错误重问一次。合并成功后待办标 `consolidated`，state 存文件 hash 清单。

映射：`memory_summary.md` ↔ `作品记忆.md`（常驻、瘦），`MEMORY.md` ↔ `设定/`（索引、按需读），`raw_memories/rollout_summaries` ↔ `work_memory_log`（库内），workspace diff ↔ hash 清单比对（作者删除是遗忘信号）。

**理由**：关键不是「让模型随手记」，而是**抽取与合并分开**——抽取只判断有没有信号，合并才决定落哪个文件。分开之后，no-op 门、证据优先、遗忘（删除）、去重才各自有明确的判定点；混在一轮里，模型会为了「显得做了事」而什么都写。**不藏在 settle 里**：settle 是账本结算，多两次 LLM 调用会让结算变慢且难解释；改成 `writing_memory` 工具，由 agent 在结算后显式调用，测试与真实链路都确定。**机械闸门先于提示词**：路径、大小、根目录都在 Python 里判，模型只产 JSON——提示词约束不了的事，代码能。

**落点**：`workgraph/memory_write.py`（输入/解析）+ `memory_guard.py`（闸门/落盘/manifest）+ `prompts/writing/memory_extract.md|memory_consolidate.md`；`work_memory_log` + `work_memory_state`（v11）；`writing_memory` 工具（status/extract/consolidate/auto）；`scripts/test_writing_memory.py`（零 LLM）+ `scripts/run_writing_memory_test.py`（真实调用）。

### 134. 沉浸阅读（点击进出）

**结论**：阅读页单击正文即进入沉浸阅读：只留正文与底部「全书百分比」状态行，侧栏、阅读器头部（含搜索）、分隔条、聊天面板、笔记浮窗、批注操作条全部隐藏。隐藏靠 `<html class="reading-focus">` + CSS，不写 inline style——退出时聊天面板的 collapsed、笔记浮窗的显隐都原样回来。退出是阅读页内任意普通点击（导航栏在模式内本就不可见）；浮层开着时点击先归浮层，搜索面板关掉的那一下不会顺手进出。Esc 也可退出。

**进入的防呆**：单击后延迟 300ms 再执行，等双击的第二下——第二下 pointerdown 取消计时、第二下 click 的 `detail=2` 被拒；拖拽（位移 >5px）、松手仍有选区、点在链接/按钮/批注 marker 上、点的不是阅读区（头部/搜索/聊天），都不算「空点」。

**版式**：chunk 模式给 `.book-page-inner` 加 `max-width: var(--t-reader-measure)` 居中；native 模式由 `_readerThemeCss()` 在 `reading-focus` 下给 iframe `body` 读同一个变量与 4% 内边距。**批注 marker（`.bc-ann-cmt`）在沉浸态照常显示**——它标记「这句上作者写过东西」，隐掉等于把批注从阅读里抹掉；marker 的点击有自己的语义（`focus-mode.js` 的 `INTERACTIVE` 里有它），气泡与编辑面板也不再列进 `html.reading-focus` 的隐藏清单，点开不会误退模式；面板里的 Esc 只关这一层（`focus-mode.js` 的 Esc 对 textarea / 面板让路），再按一次才退出沉浸。版心宽度是主题页「正文宽度」（36–72 em，默认 54）：46em 在宽屏上只占视口约 56%，留白比正文抢眼、正文像一条悬着的窄带；普通模式的整栏（无上限，约 77%）行宽又太长。用 em 而不是百分比，换字号时每行字数不变；两边必须读同一个变量，否则 chunk/native 切换时版心会跳。

**底栏**：`.left` 的 flex 子项（占 36px），不浮在正文上；`pointer-events:none` 让它也算「点阅读页」。百分比**居中**（版心是居中列，示数落在列中轴上，读作书页页脚，而不是贴在窗口左下角的状态条）。底色与正文底同源调色（chunk = 背景亮度；native = 背景亮度×字体亮度，与 iframe 宿主的 filter 同链），上缘约 1.75 行淡出（带长 = 阅读字号 × 3.1，跟随主题页 14–28px 缩放）：`::before` 用缓入 alpha 曲线（5%→14%→28%→46%→68%→实色）铺渐变色，颜色全走 `color-mix` 取底色变体。**不做 backdrop 模糊**：底栏与正文同色、看不出「玻璃」实体，模糊只会把落在带里的那一行糊成重影——早期 24px 毛玻璃罩整行正文，正是「不自然」的来源。百分比用正文墨色（同一亮度链），不再用 `--text-muted`：那个灰是按主界面底色调的，落在阅读底上对比度只有 ~1.2:1。进度与右上角 `#chunkPos` 共用 `paintProgress()`。

**占满整行**：拖过分隔栏后 `#contentLeft` 带 inline 的 `flex: 0 0 NN%`。沉浸态藏掉分隔栏与对话面板，这条 inline 却仍留白，正文只占半屏、底栏跟着缩短。用 `html.reading-focus #contentLeft { flex: 1 1 0% !important }` 压掉它——class 摘掉后作者拖好的宽度原样回来，不在 JS 里暂存/还原。

**视口**：进出都先 `stashViewport()`，宽度变化后 `resizeNative()` 按 CFI 恢复；chunk 模式按 `scrollTop / scrollHeight` 比例还原。切走阅读页时静默摘类（不做重排，并 `skipTransition()` 掉在途过渡、清掉 `focus-reveal`），由 switchTab 自己的 stash/restore 接管。

**进出过渡**：View Transitions + 共享元素（`view-transition-name: bc-book-page`，chunk/native 只挂当前可见的那个宿主）。浏览器把旧快照从原阅读区几何插值放大到全屏（退出反向倒放），组内新旧快照交叉淡化，root 负责 chrome 的隐现；430ms ease-out。⚠️ VT 的 pending 阶段会**冻结 rAF**（实测整个等待期只触发 1 次），而 native 重排链（`_waitLayoutStableThen` / `display` / 收敛）全靠 rAF——在回调里 await 重排会把过渡永久卡在 pending：页面冻结、点击落不到 iframe、iframe 也不重排。所以回调只做同步类切换并立即返回，重排放到 `ready`（新快照已拍、动画开始、rAF 恢复）之后；代价是新快照拍不到重排后的正文，于是过渡期间用 `focus-reveal` 把正文隐成书页底色，等动画与重排都完成再 180ms 淡入——视觉上是「窗口放大 → 文字从新排版里浮出来」。不支持 VT / `prefers-reduced-motion` → 直接切类（旧行为）。动画期间页面不可交互（点击落在快照上、不进 iframe）；连点/切页由 `skipTransition()` 接管，旧一轮不会揭掉新一轮的参考书B（`_vt === t` 守卫）。

**性能：先查空闲开销**。动画掉帧的根因不在过渡本身——阅读页空闲时就在烧主线程（实测 1920×1080、native 长章，空闲约 40% 单核），动画自然没有余量。两处隐性开销，修完空闲降到 ~0：
1. **图标自动刷新自激**：lucide 把 `<i data-lucide>` 换成 `<svg data-lucide>`，属性留在产物上；全局 MutationObserver 把产物当成新图标 → 再排一次刷新 → 每次重写全页 300+ 图标，形成每秒十余次的全页 DOM 风暴。修法：`refreshIcons()` 渲染后摘掉产物上的 `data-lucide`；observer 只认非 `<svg>` 的占位节点。刷新代价从 O(全页) 降到 O(新增)。
2. **导航栏图谱图标的星网动画常驻**：`animation: …` 简写会把 `animation-play-state` 重置成 `running`，与暂停开关同特异度且后写，暂停规则直接失效——每个页面都在逐帧重绘侧栏（约 15% 单核）。修法：sprite 里的 play-state 声明加 `!important`；`--gpx-play` 仍由活动 tab / 图谱加载态注入，动画只在需要时跑。

### 135. 工作区右键：文件管理归页面，正文归 agent；时间线读写作 git

**结论**：写作台左栏的工作区文件/文件夹有右键菜单（VS Code Explorer 的心智）：文件夹 → 新建文件 / 新建文件夹 / 重命名 / 添加到聊天 / 删除；文件 → 打开时间线 / 重命名 / 添加到聊天 / 删除。页面只做**文件管理**——新建空文件、改路径上的名字、删文件或整个文件夹；正文内容仍只由 `writing_docs` 写（与决策 119/126 一致：同一份东西两个写者说不清）。三个分区根（设定/计划稿/素材）不能改名或删除，作品记忆不能删；删除文件夹递归且要确认。HTTP：`POST .../docs/file`（kind=file|dir）、`POST .../docs/rename`、`DELETE .../docs/file?path=&kind=`。

**时间线**：文件的右键「打开时间线」在左栏底部向上开一个面板（VS Code 的 Timeline），列该文件的 git 历史。后端只跟第一父节点比较，等价 `git log -- <path>`；未提交改动置顶一条 `WORK`。点一条 → 主区 diff：`GET .../vcs/diff?from=…&to=…&file_path=…`，只渲染这一份文件的逐行差异；章级的恢复/撤销/摘取按钮在文件 diff 里隐藏（它们作用于当前章）。旧提交没有 `files_hash`，不参与时间线。

**添加到聊天**：发的是**路径**不是正文（正文可能很长，也不该在发送时复制），前端引用条显示「工作区文件 / 工作区文件夹」，后端 `writing_selection_block` 的 `workspace` 分支明确要求模型先 `writing_docs(action="read")`（文件夹先 `list`）再用。引用只属于写作页，切页时随写作引用一起清掉。

**理由**：VS Code 的 Explorer 本来就允许新建/改名/删除，作者不该为了建一个空设定文件去跟 agent 说一句话；但「谁改正文」必须唯一——页面不开编辑器，agent 的 `writing_docs` 仍是唯一写入口。时间线让「这份设定什么时候变成这样」可直接查，不必翻版本面板再按路径过滤；文件差异必须单文件渲染，否则同一次提交里别的文件的改动会混进来，标题与内容对不上。文件夹删除递归是 VS Code 的行为，但必须确认：目录里可能装着作者还没提交的稿。

### 136. 文件区的 git 状态徽章：M / U / D，没有 A

**结论**：写作台文件区每一行在右侧挂一个中文胶囊（`已修改` / `未跟踪` / `已删除`，对应 git 的 M/U/D），版本控制栏的文件行同款；1px 描边 + 圆角 999px + 11px 字。文件区的胶囊 `cursor: default` 并吞掉 click——点它不打开文件、不给任何反馈，只负责悬停时用 `title` 说明这个状态对这份文件意味着什么（如「未跟踪：新文件，还没有进过任何提交」）。状态在 `vcs_status` 的 `file_changes` 里逐行带 `status`（字母，给 agent）与 `status_label`（中文，给界面），前端只渲染——人工侧与 agent 侧（`writing_docs(action="list")`、`writing_git(action="status")`）读同一份。文件夹不挂胶囊，只把图标染成强调色（有后代未提交）；打开的文件在副标题里也写中文状态。

写作 git 没有暂存区：一次提交是整份工作区快照（决策 127），所以不存在 `A`（已加索引）。硬造一个 A 会和「点提交全进去」的行为自相矛盾；要 A 得先有真正的 index，那是另一个决策。

**实时**：状态是廉价的 DB 读，不经 LLM。助手跑 `writing_docs` / `writing_memory` / `writing_git_change` 时，`chat.js` 在每次 `tool_end` 调 `WritingUI.refreshStatus()`（只取 `/vcs/status`，不拉历史），文件徽章与「更改」面板当场变；整轮结束的 `refresh()` 再做一次全量对齐。页面自己的新建 / 改名 / 删除完成后也立刻重取。徽章更新只改行尾的 `<span>`，不重建树——行内改名 / 新建的输入框不会被重绘掉。

**点击**：版本控制栏点一份文件 → 中间栏显示这一份的逐行差异（`HEAD → WORK`，带 `file_path=` 只算这一份），不再跳去草稿区打开正文；看正文走文件区点文件名。删掉的文件也能点（整段删除）。

**顺手修的**：`_state_file_text` 原来拿 `commit is None` 当「工作区」，但空树（EMPTY / 还没提交过）也是 `commit is None`，于是从 EMPTY 或空 HEAD 算单文件差异时读的是磁盘，新旧永远一样。现在用显式的 `worktree` 标记区分，未提交过的作品也能看到新文件的逐行差异。另外把 `vcs_status` / `vcs_diff` 里的 `counts` 改名为 `chapter_counts`——它数的是章，和 `file_counts` 并排时被模型读成「前后矛盾」（真实 LLM 自测里 agent 直接报了这个问题）。

**理由**：状态是作者判断「这一版到底动没动」的第一眼信息，VS Code 的 Explorer 就是这么给的；把计算放在服务端而不是两个前端各算一遍，人工侧与 agent 才不会对同一份文件给出不同结论。

### 137. 版本 diff：双行号 + 整行底色

**结论**：中间栏的逐行差异按 VS Code 的内联 diff 渲染：左起两列行号（旧 | 新）。增行只走新号、删行只走旧号、上下文两边都走；增行整行浅绿、删行整行浅红，行号列比正文深一档；夜间主题换深色档。长行折行（`white-space: pre-wrap` + `overflow-wrap: anywhere`），不出现横向滚动条：一条逻辑行可以占多行视觉行，行号只标在第一视觉行，行号列底色跟着拉满整个折行块——与 VS Code 打开 Markdown diff 的 word wrap 一致。文件头（`---` / `+++`）不渲染——两端 ref 已经写在 diff 标题里；hunk 头（`@@ -a,b +c,d @@`）单独一行、不给行号。行号从 hunk 头读出并逐行推进，不信 `text_diff` 之外的东西。

解析的边界：文件头只在第一个 hunk 之前认。hunk 里以 `--` 开头的正文（「删掉一行以 -- 开头的 Markdown」）渲染成删除行，不会被误当 `---` 文件头；`\ No newline at end of file` 不给行号、不推进任何一侧。

**理由**：「改在第几行」可以直接引用，长差异里上下文和改动不会看串；整行底色比只染文字更容易扫。原先禁换行是为了行号与正文一对一，但一本小说的段落动辄两三千字，横向滚动读起来是断的，而且面板本身是自适应宽度——折行后「一条逻辑行 = 一个行号、多个视觉行」仍然对得上：行号列紧跟折行块顶端，下一个行号从下一逻辑行重新开始。

### 138. 空项目：写作页可以不绑定任何作品对话

**结论**：写作台的「切换作品」下拉顶部固定一项「空项目」（不绑定作品，先聊想法）。选中后 `workId` 置空并记在 `localStorage`（`bc.writeEmptyProject`）：刷新页面、助手工具回合结束都不会再被自动选中的第一本顶掉；只有选中某本作品才清掉标记。左栏项目浏览器显示空项目占位（空项目 / 不绑定任何作品 + 新建作品 / 选择作品）。对话仍走写作模式，`writing_work_id` 发空串。

服务端 `agent_prompt` 对空 `work_id` **不再回退到 `works[0]`**（旧行为等于把最近一本的章节、合同、工作区、版本现场偷偷注入，作者只能靠新建一本书才拿到干净上下文）。空项目块明说不代入任何一本；章节 / 合同 / 工作区 / 版本现场一概不出现。

**作品目录也不注入（2026-11-07 修）**：以前这里会列「书名（章数）id=…」，空项目会话的 system prompt 里因此带着别人书的书名——飞行记录仪实测 `记忆自测-雨夜来信 / 自测作品A` 原样进了空项目提示词，模型会顺着目录自己挑一本代入，与「空项目＝干净上下文」直接矛盾。现在只报**作品数量**，书名与 id 要看时由模型调 `writing_status`（它本来就返回全部作品）。绑定作品时同样不列其它作品；`### 最近的自测作品` 整块已删除（自测现场用 `writing_git(status)` 现查，见 platform.md 决策 90 的 2026-11-07 修）。工具侧 `_resolve_work` 在没绑定时报「先 writing_create_work 建书，或请作者在左栏选一本（已有作品用 writing_status 看）」。助手在空项目里建了书，回合结束的 `refresh()` 会选中新书并自动退出空项目。

**空项目不显示版本控制（2026-11-07）**：素材库是全局原料仓，**不进写作 git**（决策 156），空项目没有可提交的作品，版本控制在这个状态下没有对象。左栏「版本控制」药丸与头部分支徽章一起 `hidden`（`renderNav` 按 `S.workId` 判定，两处自带 `display`，CSS 要显式让位）；若切换时正停在版本控制，先回项目浏览器。

**理由**：作者需要一块「不预设任何一本」的讨论区——聊题材、试开场、比两个方向的做法，这时任何一本的设定都是污染；空白上下文应该是一个可显式选择的状态，而不是「再建一本垃圾书」的副作用。写作用户界面与 agent 的现场必须同源：界面显示空项目，提示词里就不能出现某一本的正文。

### 139. 写作会话按作品收录，且只属于写作页

**结论**：写作页的会话导航只有两个页签——**全部 / 按作品**（原来的「按书籍 / 按角色」对写作会话没有意义）。「全部」是写作这条线的会话平铺列表，按时间倒序；每行 meta 里的「写作」换成作品名（没绑作品的显示「空项目」），标题上不再挂作品胶囊。「按作品」是作品卡片，点进去才是这一本的对话列表。绑定为空的作品（空项目里聊出来的、以及迁移前的老写作会话）归到「空项目」组，排在最后。页签切换用 `.session-subnav.is-writing` 的 CSS 收显，不能用 `hidden` 属性——`.session-subnav` 自带 `display:flex`，会盖掉 UA 的 `[hidden]{display:none}`。其它页面的会话导航彻底看不到写作会话：列表与全文搜索都带 `exclude_mode=writing`，写作页签从 DOM 里删掉。

数据上，`sessions` 新增 `work_id` 列（迁移 14，常量默认值 `''`，带索引），写作消息每轮把当前作品写进去（空项目写空串）。服务端列表顺带返回 `work_title`（从 writing.db 取），前端不额外拉作品表。会话线指针 `bc_tab_sessions.write` 增加 `workId`：回到写作页先按它恢复作品，空项目的空串也照原样恢复。

「换作品」在写作页是**显式结束这条会话线**（`clearTabSession('write')` + `resetChatView()`，与阅读页换书重开同一条规则），旧对话留在原作品组里，随时能从面板点回来；点某本的会话时写作台跟着切到那一本（`WritingUI.openWork`），否则提示词与历史会来自两个作品。程序性选中（助手建书后刷新、自动选第一本）不结束会话线。

**理由**：写作对话天然属于某一本——人物、合同、设定都不同，混在「全部」里既找不到也不好续写；把它整个关在写作页内，主页/阅读页的会话列表才回到「读书与闲聊」的语义。分组用作品而不是平铺，是因为作者找回一段对话时先想到的是「我在写哪本书」。

### 140. 批注气泡：正文下划线指回，气泡不再抄原文

**结论**：点开批注角标（`.bc-ann-cmt`）时，当初被批注的那段文字在正文里临时画出蓝色下划线（`g.bc-ann-underline`，与角标同色 `#3b82f6`）；气泡里不再重复 `selected_text`——「这条批注指的是哪句话」由正文回答，气泡只留批注内容与「编辑 / 删除 / + 新增批注」。下划线跟气泡同寿命：点任意空白处、点另一个角标（旧气泡收起、旧角标翻回、新气泡展开）、再点同一个角标、Esc 都撤掉；点「编辑 / 新增」时保留到面板关闭，免得写批注时失去上下文。

**滚轮不收盘**：气泡是 `position: fixed`、开在角标的视口坐标上，早先靠「滚动即收起」掩盖它会脱锚的问题——但读批注时滚一点看看上下文是常态，第一下滚轮就关掉很反直觉。现在滚动只收选区浮动条，气泡在 `scroll` 捕获里用 rAF 节流重算角标视口坐标（`_followOpenBubble` → `_placeBelow`）跟着走；角标滚出视口时气泡**停在最后一处、不收**，收起的入口只有「点空白 / 再点角标 / Esc」。

跟随锚不能是节点：section 重渲染（面板开合、长滚动后的卸载重建）会把角标元素整个换掉，而旧节点仍留在自己那个已经脱挂的 document 里，`isConnected` 照样是 true。所以气泡记的是组键 `_bubbleCfi`，`_markerLive()` 额外校验 `frameElement.isConnected`；重渲染时 `_replayCommentsInContents` 让新角标直接接管并翻上（`_openMarker` 换新），滚动时按组键 `_findGroupMarker` 找回，拿不到就停在原处等它回来。

空白处点击的兜底挂在 iframe 文档的 `pointerdown` 捕获上（`_armDismissOnDocPointer`，`showGroupBubble` 时补挂，不依赖选区钩子——没拖过选区的页面同样能收起），角标自身的 `pointerdown` 除外。收起气泡的那一下写 `window._bcOverlayClosedAt`，沉浸阅读的 `_overlayGraceActive()` 据此把这次点击让给浮层，不会「关气泡顺便退出模式」。

**角标是开关**：再点一次同一个角标就收起（走 `_hideBubble`，与点空白 / Esc 同一条收尾路径：预览下划线一起撤、角标 morph 翻回）。判断依据是 `_markerState` 里的 `open`，不是气泡的显隐——刷新过的组、图片式的旧气泡都由此统一。

**理由**：原文抄进气泡有两个开销——气泡首屏被引用占掉一半，且读者还得自己回正文找那句话。正文里那道线才是批注的锚：角标只是「这儿有批注」的索引。预览线与收藏走同一个自绘层（决策 163）：`_underlineCfi` 当账本，`_redrawMarksInContents` 逐文本节点取行框、贴字画线，section 重渲染会自己补回来；同一 CFI 已有收藏下划线时不再叠第二条（已有线即锚）。

### 141. 重排前后复位连续补载队列（收起/展开交互页后翻不动）

**结论**：`resizeNative` 与 `restoreViewport` 在调 `rendition.resize()` 的前后各执行一次 `_resetManagerFillQueue()`：`q.stop()` 清空积压、复位 `running/paused`，随后由 `_kickContinuousFill()` 重跑一次 `check()`。

**理由**：fork 的 `ContinuousManager.resize` 一旦宽度变化就同步 `clear()`（`views.hide()` + `scrollTo(0,0,true)` + `views.clear()`），把全部 view/iframe **destroy**。而 `offset: 8000` 的预读让补载 `check()` 几乎一直在飞，它正 `await Promise.all(views.map(v => v.display(request)))` 那批 view。iframe 被 destroy 后 load 不再触发，Promise 永久 pending → `manager.q` 队头卡死，之后每次滚动 enqueue 的 check 全排在死任务后面（实测收起后 300ms 积压 14 条、展开后 46 条），补载不再执行；容器里只剩 `display(cfi)` 渲染的那一个 section，滚到底就顶墙，表现为「收起再展开后阅读页无法上下翻动」。

这是时序竞态而非编译差异：打包版改变资源加载节奏，恰好每次都输掉这场竞争；无头脚本在源码上同样每次复现。`check/update` 幂等，丢弃积压任务无副作用——复位后实测 views 1→16、滚动恢复、位置（CFI）不丢。

### 142. 写作工作流：阶段诊断 + 行为簇，不做固定流水线

**结论**：写作编排拆成三段——认知段（世界 / 人物 / 定调 / 搭骨）没有顺序，只有行为菜单；落章段（合同 → 正文）半线性；机械段（结算 → 校验 → 提交）必须线性。`prompts/writing/agent.md` 的「默认工作顺序」改成「你在哪，下一步做什么」的行为表：先由 system prompt 的「当前写作现场」诊断作者正在做什么，再只做那一件；**只补这一章用得上的一块，不要求世界层完整**。现场新增「现在在哪」块（已有 / 世界层 / 账本 / 缺 / 可做 / 建议），由工作区、章节、合同、承诺与 `设定/世界.md` 的 facet 状态算出，只给事实与选项，不强制下一步。世界层落 `设定/世界.md`，六个起步 facet（时代与地理 / 社会结构 / 经济运转 / 文化与日常 / 时代情绪 / 故事窄口，不够可加），每个 facet 带 `状态：定|悬|隐` 与 `可见：读者已见|仅作者`；只记作者说过的，agent 可以给「如果……会怎样」的候选，作者点头才写。素材按四源分级消费：本作正典 > 已入库书（`writing_research` 关键词或语义检索一条细节，`writing_references` 整本借写法）> 训练知识（只给可能性与质感，不当可核查事实）> 联网（DeepSeek Search / Fetch，见决策 145）；找素材先定需求类型、query 不用本作人名、只给 1–3 条带出处的候选。减法靠合同 `withhold`（「可以写但不点破」；旧合同的 `forbidden_cross` 以「不点破：」开头的仍认）与结算摘要的第二句「读者新知道：…」承载；读者已知暂不建表，先由 `chapter_summary` 第二句落进 `chapter_summaries.summary`（下一章卡片自动带上），`close_note` 留副本；「现在在哪」读上一章摘要第二句、退回 `close_note`，输出一行「读者已知」。等审稿要机械检查时再拆独立字段。

**理由**：作家的行为不是一条流水线——常常写到第 5 章才想明白第 1 章的时代；把认知段做成阶段门禁，会把「想清楚 demo」这件真正有价值的事挤成填表。反过来，机械段又不能交给模型自由发挥：没有合同不写、写完不结算不进下一章、结算被拒不绕过账本，这三条是账本有效性的前提。世界层的判据不是「写全」，而是能回答四类反事实（靠什么活着 / 怎么处理 / 怎么说 / 什么算反常），所以允许 facet 空着、允许边写边长；三态把「已决定 / 故意没定 / 作者知道但读者不知道」分开，agent 才不会替作者补全，也不会把吃水线以下的东西说破。素材分级是因为训练知识最便宜但最不可核查，参考书可逐字引用但会带专名，联网最贵但能核实具体事实；不分开就会把「模型的印象」写成「这个时代的事实」。

### 143. 阅读进度：行级锚（字符偏移 CFI）

**结论**：`_captureViewport` 建 CFI 时不再从文本节点开头（`:0`）起，而是取「视口顶第一个完整可见行」的行首字符偏移 `:N`；恢复链不变（`display(cfi)` + `_scrollToCfi` 已能按 Range 实际位置精修）。服务端不再按 `(chapter, chunk)` 提前丢弃同一块内的上报：`record_position` 在同一块内**原地更新**最后一条的 `cfi/ts`（空 cfi 不覆盖已有细锚），只有跨块才 append，`positions_json` 不会因滚动膨胀。

**理由**：旧链路有两处粗化——抓锚恒取 `:0`（等于段首），且 `/api/sync` 只在 chunk 变化时落库（同一块内停在哪行根本没存）。字符偏移是文本坐标，换字号、版心、窗口宽度后仍指向同一行；相比之下像素偏移只对「当前版式」有意义，换版式就变成错误坐标，所以不做像素级持久化。

行首的选择是**第一个 top >= 视口顶**，不是「跨过视口顶」的那一行：恢复时 `_scrollToCfiLoop` 刻意把锚落在视口顶下方 24px，跨过顶部的其实是上一行露出的尾巴；按它取锚会让每次重开向上退一行，反复开关形成棘轮。实测：抓锚偏移 94 → 重开恢复 94 → 再次重开仍 94（三轮不变）。

旧记录（`:0` 或无 cfi）照旧走段落级恢复，读一次就被新锚覆盖，无需迁移。

### 144. 阅读页注入视窗文字，而不是单块正文

**结论**：阅读页发消息时前端抓「视口内实际渲染的全部文字」——跨 section 拼接、首尾按行裁切（`captureViewportText`），随 `/api/chat` 以 `reading_viewport: {text, sections:[{sectionIndex, visiblePx, text}]}` 发出。后端 `<current-passage>` 优先用它，不再只给 `(chapter, chunk)` 那一块：按候选章把 chunk 正文拼成规范化串，用视窗文字开头定位，再把块边界映射回视窗文字，逐段标注「第 x/y 块 · 章名 · 块内约 a% 处起/止」。单块时写明「完全落在这一块内」；跨块时写「共跨 N 块」；跨章再写「跨 N 章」。对齐失败（重导、改字）不降级回单块——原样送出视窗文字并注明「块边界未知」，避免模型看到的比读者少。没有视窗文字（旧客户端 / chunk 视图）才退回原来的单块注入。

**理由**：一屏正文常横跨 2–3 个 chunk，单块注入时模型看到的内容比读者屏幕上少，回答会漏掉视窗下半段；而位置坐标只说明「读到哪一块」，不说明「屏上是什么」。视窗文字是读者已经看见的第一手证据，也天然与剧透门一致（可见章即已见）。

候选章 = `visible_chapters`（/api/sync）+ `reading_viewport.sections` 的 `sectionIndex` 经 `_section_chapters` 映射 + 阅读进度章；首轮没命中就以这些章为种子外扩 ±1、±2 章再对。**结构映射只当候选、不当真相**：实测部分书的 DB `spine_index` 与渲染器 `sectionIndex` 差位（参考书A渲染 section 21 落的是 chapter 20 的正文），对齐必须以文字本身为准。

已知未覆盖：语音消息（`sendVoiceMessage`）不带 position/视窗；roleplay 不注入阅读现场（沿用旧规则）。

### 145. 写作联网：DeepSeek 原始 Search/Fetch，授权 + 每轮 2 次 + 落素材

**结论**：写作的联网不接 `web_search_service.py` 的 Anthropic 兼容原生搜索，而直接调 DeepSeek `POST /v1/tools/search` 与 `/v1/tools/fetch`（`services/web_research_service.py`）：前者回 `results[]`（title / url / snippet / summary / content / site_name / date / authority / rerank_score），后者回整页 Markdown。根地址从 `api_base` 的 host 推（必须落在 `deepseek.com`，不偷偷换供应商），key 同 `api_key`；主模型不是 DeepSeek 时，从控制台连接里找 `base_url` 落在 `deepseek.com` 的那条（`ProviderStore.reveal_key`），找不到就原样报错，不回退别家。素材卡归一后按 `rerank_score` 排序；`content` 非空才算「网页正文」，只有 snippet/summary 的是「搜索摘要」（`exact=false`），两者都带 URL、站点、日期、权威性与「外部来源」警示。`writing_research` 扩成 `source=library|web|auto` + `url`（直接抓页）+ `enable_web`（本轮作者授权）+ `save`（写进 `素材/网络/<日期>-<词>.md`，带 URL 与逐字引文）；`auto` 先书库，空了且已授权才联网。授权有两条来源：作品 `style_profile.web_research_enabled` 开关，或作者本轮明确要求（agent 传 `enable_web=true`）；未授权由代码拒绝，不靠提示词自觉。每轮最多 2 次（请求级 `ctx["_web_research_calls"]`），auto 在预算用满后退回书库。408/429/5xx 等 1.5 秒重试一次。

**理由**：写作只需要两件事——可核查的外部事实（年代、物价、职业流程、方言）与可引用的原文，不需要一个「搜索后由模型总结」的黑箱。原生 web_search 只回结果块，拿不到稳定的 URL / 正文对照；DeepSeek 的原始接口给出结构化来源与整页 Markdown，正好能落成带出处的素材卡。只认 DeepSeek，是因为计费与配额都在同一条连接上，混用 Tavily 会让「这次搜索花了谁的钱」说不清；`api_base` 不是 DeepSeek 时明确报错，比静默回退更好。授权必须由代码守住：agent 很容易在「帮作者省事」时自己开网，而联网是外部副作用（花钱、把作品信息发出去），和写文件不是一类操作。落到 `素材/` 而不是直接进上下文，是因为素材只是候选，作者与 agent 要一起挑合并项；`save` 默认关闭，避免每次检索都把素材库塞满。

**不做的**：不把搜索摘要当逐字引文；不接 embedding 召回（可选来源，当前不做）。空项目的落盘改走全局素材库（决策 156）。

### 146. 章表 spine_index 必须存 OPF 坐标（渲染器坐标），不是 reader 压缩坐标

**结论**：`book_chapters.spine_index` 一律写 **OPF spine 里 itemref 的原始序号**——即 epub.js 的 `sectionIndex`。`EpubReader._spine_ids` 为了跳过封面/目录等非正文项会压缩下标（`_NON_CONTENT_IDS` / `_NON_CONTENT_RE` / HREF 规则），这个压缩坐标只供 reader 内部（TOC、深度、读原文、切分）使用，不能落库。`EpubReader` 新增平行数组 `_spine_opf_index`（内容下标 → OPF 下标）与访问器 `opf_spine_index()`；`epub_import_service` 落库时换算。历史数据用 `scripts/backfill_spine_index.py` 回填：默认演练，`--apply` 前自动备份 books.db。

**判据**：epub.js `parseSpine()` 对 `<itemref>` 逐个编号（`linear="no"` 也不剔除），`unpack()` 按数组序号建 Section，所以渲染器的 `sectionIndex` 恒等于原始 itemref 序号。脚本按「章正文开头是否出现在该 spine item」投票区分库里存的是压缩坐标还是 OPF 坐标；旧导入的 `-1` 行按「恰好一个 item 命中」反推（多义留 -1，走指纹兜底）。回填幂等：修过的书复跑投出 opf，计划改动 0 行。

**理由**：错位时 `/api/sync` 的结构定章与 `reading_viewport.sections` 的 `_section_chapters` 会整体偏一到两格（跳项越多偏得越多），静默退回文字指纹；短章/重复句多时指纹会认错章，剧透门与视窗注入跟着错。实测参考书AOPF spine 24 项、reader 23 项（titlepage 被跳），section 21 曾映射到 chapter 20（第八章对第八章的下一章）。回填后 section 21 → chapter 20（第八章）正确对齐。

**不做的**：不改 `_spine_ids` 本身去包含前置页（会改变章节切分、目录与导入行为）；不在读取时实时打开 epub 反推（成本高、并发差）——坐标在写入时一次算对。

### 148. 语义召回走 embedding 槽位，向量独立成库

**结论**：写作素材的第二条召回路径：`writing_research(source="semantic")` 把查询与书块向量归一化后做余弦近邻，返回与关键词检索同形的候选卡（`recall="semantic"`、`kind="语义近邻"`、带 `chunk_id` 与 `score`）。embedding 端点为控制台「模型绑定 → Embedding」的当前槽位（`ProviderStore.resolve("embedding")`），没绑定才回退 `EMBEDDING_*` 环境字段；两者都没有时明确报错，不猜供应商。向量存 `data/embeddings.db` 的 `chunk_vectors`（主键 `chunk_id + model`，存 `content_hash / book_id / chapter_index / dim / float32 归一化向量`），不进 `books.db`：向量是写作侧的派生物，不该跟着书库迁移；`content_hash` 不匹配时下次建索引重嵌；删书留下的孤儿向量在回读正文时跳过。索引由 `scripts/build_embedding_index.py` 增量构建（默认全库；`--book` / `--limit` / `--dry-run` / `--force`；每批完成即落库，限流中断可从断点续跑）。检索时模型不匹配返回空并说明，不拿旧模型的向量凑数。`auto` 仍是关键词 → 联网（156 后前面多查一次素材库），语义必须显式选：不让一次「书库没命中」悄悄触发一次外部调用。

**理由**：关键词（FTS/LIKE）命中的是字面词，适合行话、物象、制度名；语义命中的是意思，适合「说不出口的愧疚感」这类没有关键词的意图，两条路都只借写法与细节、不改变素材分级。用当前绑定的 embedding 槽位而不是硬编码 provider：控制台换模型时语义召回必须跟着换，否则会拿 A 模型的向量去比 B 模型的查询（空间不可比）。向量独立成库，是因为 `books.db` 的 schema 归导入链路，而向量会随模型、重导、索引策略频繁重建；单独文件也让「删掉重来」只动派生物。归一化后存 float32 是性价比选择：2048 维 × 6k 块约 49MB，点积就是余弦，numpy 暴力检索足够；规模再大才需要 ANN。索引必须显式建、语义必须显式选，是因为「没有索引 / 模型换过」时的静默降级会给出看似相关实则无关的候选，比没有结果更坏。

**真实联调**（2026-11-04）：当前绑定 `火山引擎coding plan / doubao-embedding-vision`（2048 维）。参考书A67 块 4 秒建完；查询「为了信仰放弃爱情，把克制和痛苦当成一种美德」返回参考书A第 20/19 章，余弦 0.4254 / 0.4223。全库索引在后台增量建立时，用当时已覆盖的 8 本 / 1737 块做跨书测试：查询「把全部热情寄托在另一个人身上，最后发现对方只是普通人」返回参考书A第 19 章（0.3788）、《克拉多克太太》第 23/34 章（0.3659 / 0.3640）、《参考书B》第 81/31 章（0.3626 / 0.3558）；同题关键词检索（6 个词）前三却是《百年孤独》《卡拉马佐夫兄弟》《当下的力量》，只命中零散字面词。语义路径按意图把「理想化的爱 → 幻灭 → 普通伴侣」排到了一起。

### 156. 全局素材库：文件做原料仓，索引记录消费，树只做分类

**结论**：新增**不属于任何作品**的全局素材库（`data/writing/materials/`），与作品工作区的 `素材/` 分开：

- **三层**：素材库（跨作品原料仓）→ 作品 `素材/`（这本书的短名单）→ `设定/`、正文（真正用掉）。库负责攒，作品素材负责选，设定正文负责用。
- **文件而不是库表**：一张卡一个 `.md`，作者能用任何编辑器打开、备份。卡片抬头可读、可正则解析：`素材 <id> · 出处 · 采集时间`、`分类：情感/爱情/离别`、`标签：…`、`收录：作者指令 · 会话 …`、`指令：作者点名时那句原话`；正文只有 `## 原文` 与 `## 说明`。**不写「适用于……」**——检索靠分类、标签和原文，不靠用途 prose。
- **身份是摘录哈希**：`material_id = sha1(归一化原文 + 出处)[:12]`，文件名 `<hash>-<短标题>.md`。改名、换分类、编辑说明都不改身份；同摘要同出处重复收录返回原路径。
- **分类是一棵主目录树，标签补其余维度**：一条素材只有一个主分类（`人物 / 情感 / 场景 / 社会 / 语言 / 时代 / 事件 / 写法 / 待归类`，作者可增删），一棵树只能有一个父亲；跨维度靠 tags。
- **生产两条主路**：① 作者点名收录（「把参考书A里那段诀别信收进素材」）——先定位到具体 chunk，再 `writing_materials(action="intake", source="book", chunk_id/book_id+chapter_index+chunk_index)`，以库里逐字原文为准；② 写作中召回并**实际决定用**的一段顺手沉淀，带 `origin_work_id`。只收真正要用的，不收搜索命中的全部；agent 无目的找素材不做，但工具不封。
- **索引粒度到段，不等同于阅读粒度**：阅读工具按 chunk 取原文，但 chunk 常是「一封信 + 后文」。`read_chunk` 把块按空行切成带编号的段落（`split_paragraphs`），`intake` 收 `para_start` / `para_end`（1-based，含两端），服务端用 `paragraph_span` 从库里的原文切——**不接受模型转述或自己截的字符串**。出处行写成 `块 #2 · 第 3–9 段`；身份仍按「切出来的原文 + 书章块」算（`source_ref` 不含段落措辞），同段重复收录照常去重。整块收录不传段落参数，行为与旧版一致。
- **消费用连线表，不用分支、不把消费做成目录**：`material_uses(id, material_id, work_id, kind, chapter_id, target_path, note, session_id, created_at)`（`writing.db` 迁移 13）。`kind` 分 `shortlist`（复制进作品 `素材/`）/ `merge`（进设定）/ `inline`（进正文）；`note` 写这部作品怎么改的。素材本体不进写作 git；消费记录是作品侧的事实，随作品删除。素材改名/换分类不影响连线；删进回收站后历史仍在。
- **提升是复制不是挂链**：`materials_promote` 把卡复制进作品 `素材/`，抬头加 `取自素材库：<原路径>`。作品要自足——库被清理或换机后，这本书的历史仍说得清出处；原件留在库里不退场（决策 130）。
- **消费顺序**：本作正典 → **本书 `素材/` + 全局库** → 已入库的书 → 训练知识 → 联网。`writing_research(source="materials")` 查库；`auto` 也先查素材库再读书库。库的可信度按卡上出处判断，不统一抬成事实。
- **边界**：不进写作 git、不自动召回、不自动进上下文；空项目也能收录（联网 `save=true` 落全局库，不再报「没有工作区」）；删除进 `_回收站/`，不硬删；页面可直接编辑素材卡正文（原料不是正典），作品 `设定/`、正文仍只由 agent 写。

**理由**：为什么不是分支——分支假设同一条素材有多个版本、还能合并回主线；这里的适配是作品自己的产物，永远不会合回素材库，素材卡是不可变快照（要改就是新卡新 id），没有 merge/rebase。为什么不是目录树——一棵树每个节点只有一个父亲，而一条素材会被多部作品消费；把消费做成目录，分类和出处就混在一起，改一次归类要动一批消费记录。索引负责「去了哪」，树负责「是什么」，两者只在展示层合并（素材 → 作品改编）。为什么坚持文件——作者要能备份、搬走、用自己的 git；为什么不做全自动召回——素材的价值在于作者和 agent 一起挑，自动召回会把它变成噪声源，还会把同一段反复塞进每章。为什么身份不跟路径——改名/换分类是常态，连线必须跟内容走。

**落点**：`writegraph/materials.py`（卡片格式、哈希身份、检索、收录、回收站、读 chunk、`split_paragraphs` / `paragraph_span`）；`storage/writing_db.py` 迁移 13（`material_uses`）；`services/writing_service.py`（`materials_*`、`search_materials`、`_save_web_cards` 空项目落库、`research_material` 的 `source=materials` 与 `auto` 顺序）；`writegraph/chat_tools.py`（`writing_materials`，写作工具集第 18 个）；`api/routes/writing.py` + `api_server.py`（`/api/writing/materials/*`）；`reader/js/writing.js`（空项目左栏素材库、有作品时的固定入口、卡片阅读与编辑）；`prompts/writing/agent.md`（素材库一节、五源顺序）。测试 `scripts/test_materials_library.py`，已进 `check_all`。

**不做的**：M0 不做阅读页「选中即收录」、不做消费视图、不做库内语义检索。作品侧联网落盘仍是旧的 `素材/网络/` 单文件格式，统一成卡片格式留到 M1。库内文件管理见决策 157（重命名 / 换分类 / 删除进回收站）。

### 157. 素材库维护：回收站闭环、改名换分类、审计只报告

**结论**：维护动作全部显式触发，不在启动时自动跑，也不自动合并/自动淘汰。

- **回收站闭环**：删除仍是移进 `_回收站/<时间戳>/`，但现在带 `manifest.json` 记**原始相对路径**；`restore` 默认放回原分类（也可给 `target`），`purge_recycled` 默认清理 90 天前条目。旧版扁平回收站仍能恢复（按卡片抬头 `分类：` 放回）。清理只由页面确认后调用或脚本 `--apply`，agent 工具不暴露 purge。
- **回收站垃圾桶 = 清空回收站（2026-11-07）**：页面右上角那枚垃圾桶原来只清「90 天前」，刚删的条目点了没反应，看起来像坏键。现在页面按钮显式传 `all=true`（`days=0`，确认框带条目数，删除后无法恢复），脚本与审计仍按 90 天保留期；两者都是显式动作，不做自动清理。
- **回收站不画在素材库的缩进线里（2026-11-07）**：回收站组挂在「素材库」组的末尾，而不是分类子级容器里——之前一条素材库的 indent guide 会越到回收站及其条目下面，看起来像没有归属的竖线。分类子级容器的参考线现在只罩分类。
- **清空文件夹（2026-11-07）**：素材库文件夹右键新增「清空文件夹」——把该文件夹（含子分类）里的所有素材卡逐张移进回收站，**文件夹与子分类本身保留**；每张卡有自己的 manifest，恢复回原相对路径。不是硬删，清理仍走回收站；文件夹里没卡时菜单项禁用。
- **改名 / 换分类**：`rename_entry` 之外新增 `move_entry`，保留文件名与身份。agent 工具 `writing_materials(action="rename"|"move")`，页面库树右键（重命名 / 移动到… / 删除）。**不要删了重收**：重收会换 `material_id`，`material_uses` 连线就断了。
- **审计只报告**：`audit` 返回未消费（含 90 天未动）、近重复候选（同原文跨来源 / 同出处近似）、身份重复、坏抬头（缺身份或分类）、原文被改过导致身份对不上（按抬头还原出处后重算哈希）、回收站积压。页面和 agent 都只展示候选；合并不做，清理不自动做。
- **成本**：消费计数一次 `GROUP BY` 查询（`material_use_counts`），不按卡逐个查；回收站一次目录遍历。

**理由**：「phase1 抽取 → phase2 合并」两段式，配 watermark、全局锁、无操作门、保留期与合并输入上限。可迁移的是**维护动作骨架**：显式触发、增量、保留期、报告与执行分离、上限。不可迁移的是自动合并与自动淘汰——素材卡是作者挑的不可变快照，自动合并会破坏「同一段被多部作品改编」的连线语义（156）。

**落点**：`writegraph/materials.py`（`move_entry` / `empty_dir` / `list_recycled` / `restore` / `purge_recycled` / `recycled_summary` / `audit`）；`storage/writing_db.py` 的 `material_use_counts`；`services/writing_service.py` 的 `materials_move/empty/restore/recycled/purge_recycled/audit`；`writegraph/chat_tools.py`（rename/move/recycled/restore/audit，无 purge）；`api/routes/writing.py` + `api_server.py`（`/materials/move|empty|recycled|restore|purge|audit`）；`reader/js/writing.js`（回收站节点与右键菜单、`emptyLibraryFolder`）；`scripts/maintain_materials.py`；`prompts/writing/agent.md`。测试 `scripts/test_materials_library.py` / `scripts/test_materials_empty.py`。

### 158. 参考素材由 agent 选坐标，服务端只读原文

**结论**：删掉写作前的「自动召回 + 蒸馏」隐藏管线；素材查找回到读工具语义，agent 串行检索（或以后由子代理并行检索），把选中的坐标交给 `writing_draft_chapter(refs=[...])`，服务端按坐标读回**逐字原文**注入本章。

- **refs 是什么**：书块 `book_id + chapter_index + chunk_index`（可选 `chunk_id`，可选 `para_start/para_end` 只取块内几段），或素材卡 `material_id` / `path`；每条可带 `note` 说明借来做什么。`WritingService.resolve_refs` 用 `materials.read_book_chunk` / `read_card` 读原文，不摘要、不改写、不跨条合并。读不到的坐标直接报错（`写作装配前拦住`），不做静默降级。
- **不再有数量帽**：`set_reference_books` 原 `clean[:4]` 已删；`writing_references` 只是**书架/检索范围**，不再在写稿时自动注入，`reference_mode=card/raw` 不再参与写作路径。作者说「照《X》」时，agent 用 `writing_research(book="X")` 限定检索（关键词与语义两路都支持 `book_ids`）。
- **预算只剩装配器总预算**：refs 渲染进 `external_reference` 块（900 tokens / 900 字预算），装不下由 `budget.compile_blocks` 截断或丢弃并在 manifest 标原因；`writing_draft_chapter` 返回 `reference`（条数/字数）与 `context`（dropped / truncated），agent 据此自己减 refs。没有按书数或来源数的预算。
- **为什么**：素材查找是读文件工具的应用，不是上下文编译器。旧设计在 `stream_chapter` 里自动召回并调一次 LLM 蒸馏，是因为主 agent 的上下文传不进另一次 draft 调用；那条「断桥」补上后，隐藏管线与它带来的 4 本帽、2400 字 skeleton、520 字卡都不需要了。混合多本书的问题也不是「腔调被平均」，而是出处被合并——按坐标逐条注入天然保留出处。

**代价**：agent 不找素材就没有参考素材（这是正确行为，但结果与旧的自动卡不同）；writebench 的 `ref_hybrid_v2_len` 基准需要重跑后再判断优劣。并行子代理见决策 159；串行路径已可用。

**落点**：`services/writing_service.py`（`resolve_refs` / `assemble(refs=)` / `stream_chapter(refs=)`、删除 `distill_reference` 与 `_reference_cache_path`、`set_reference_books` 去帽、`research_material(book=)`）；`writegraph/reference.py`（`search_library(book_ids=)`、`render_refs`）；`writegraph/chat_tools.py`（draft `refs`、research `book`、references 描述）；`prompts/writing/agent.md`；测试 `scripts/test_writing_refs.py`。

### 159. 写作页的素材侦察子代理：只检索，只回坐标

**结论**：写作页多一个 `writing_researcher` 子代理。主 agent 在需要多个互不重复的素材方向时，用 `Agent(subagent_type="writing_researcher", description=…, prompt=…)` 把「去书库/素材库找几条能借的原文」整包丢出去；子代理只拿回 `{"refs": [...], "notes": "…"}`，主 agent 把 `refs` 原样交给 `writing_draft_chapter`。

- **工具白名单**：`SUBAGENT_TOOLSETS["writing_researcher"] = ["writing"]`，再用新增的 `SUBAGENT_INCLUDE_TOOLS` 收成只有 `writing_research`。写作工具全注册在同一个 toolset 下，只按 toolset 过滤会把 `writing_draft_chapter` / `writing_settle_chapter` 一起交给子代理，所以必须有名称白名单（`get_registry_for_toolsets(include_tools=…)`）。`Agent` 本身在 `CONTEXT_CREATING_TOOLS` 里，挡住递归。
- **请求级重注册**：基础注册表里的 `Agent` 闭包捕获**基础**工具表（没有写作工具），直接暴露等于给子代理一张空表。`build_writing_registry` 在请求级副本上再注册一次 `Agent`，`default_type` / `allowed_types` 只有 `writing_researcher`，`streaming=False`。
- **不回传中间话**：子代理的 `run_stream` 会把每段中间推理都塞进主 agent 的工具结果。写作页关掉 `execute_stream`，只走 `execute_async` 并压成坐标；用户仍能看到 `[🔧 Agent...]`。
- **坐标先验一遍**：`_writing_agent_result` 用 `llm_json.loads_tolerant` 读子代理最后的 JSON，再逐条 `resolve_refs` 试读；读不到的单列 `dropped`，不让死坐标流进 draft。解析不出 JSON 时标 `parse_error` 并附原文尾部，不编 refs。
- **本书 `素材/` 也能当 refs**：`resolve_refs(work_id=…)` 在全局素材库找不到 `path` 时回查作品工作区（`search_materials` 返回 `library=work` 的卡没有全局身份），出处标「作品素材 · …」。
- **子代理的联网口径**：只沿用它已有的 `enable_web` 闸门；提示词明确「任务没写作者已授权就不联网」。它和主 agent 共用请求级 `ctx` 的联网计数（每轮最多 2 次）。

**理由**：找素材是读工具应用，串行的成本是「结果全压在主线上下文里」，并行的成本是「子代理看不见主线的推理」。把子代理限制成只有检索、只回坐标，正好让后者只承担「去哪儿找」这一小段；素材正文仍由服务端在 draft 时读回，出处不丢。不默认并行（也不承诺同一轮的工具调用真并发）：只有一两个检索词时自己调 `writing_research` 更省，子代理是为「多方向、互不重复」准备的。

**落点**：`sub_agent/types.py`（`writing_researcher` / `SUBAGENT_INCLUDE_TOOLS` / 提示词与迭代预算）；`sub_agent/__init__.py`（`include_tools`）；`tools/registry.py`（`get_registry_for_toolsets(include_tools=)`）；`tools/agent.py`（`default_type` / `allowed_types` / `streaming` / `result_transform`）；`writegraph/chat_tools.py`（请求级 `Agent` 注册、`_writing_agent_result`）；`services/writing_service.py`（`resolve_refs(work_id=)` 回查作品素材）；`prompts/subagent/writing_researcher.md`；`prompts/writing/agent.md`；测试 `scripts/test_writing_refs.py` / `scripts/test_writegraph.py`。

### 160. 写作页的回合时间线：工具调用默认收起的三层折叠

**结论**：写作页的 agent 回合不再只有「思考行 + 气泡」，而是一张可折叠的时间线——L0 `已完成 · 27分1秒 ⌄`，点开是 L1 步骤流（思考 / 旁白 / 工具行），工具行再点开是 L2（一行摘要 + `<details>` 里的原始输出）。其他页面保持原样。

- **只给写作页**：`state._turnTrace` 只在 `writingCtx` 下建。阅读页/主页的工具调用仍不渲染——那里的对话是读者与留白，不是 agent 工作记录；写作页一轮几十次读写，没有时间线就只剩「思考中…」的空白。
- **回合头默认收起，流式时展开**：点击时间线内任何位置都记 `_traceTouched`；结束时只有「没被操作过」才自动收起（作者动过就说明正在看，不抢）。
- **旁白进时间线**：`tool_start` 是天然的轮次分隔符。收到它时把当前气泡正文冻成 `.turn-narration`、气泡归零；最后一轮没有工具调用的正文才是最终回答，留在气泡里。不需要新增 `round` 事件。
- **标签由后端白名单生成**：`tool_start` 带 `label` / `kind` / `id`，`tool_end` 带 `id` / `preview` / `summary` / `ok`。对象只从 `chapter_index` / `path` / `query` / `title` 取——原始 `arguments` 里装着整章正文，绝不上屏；前端只当文本用，不 `insertHTML`。
- **回放同一条线**：`sessions.py` 在 `mode=writing` 时把一轮 ReAct 的 thinking/text/tool_use 按块序存成 `steps`，工具结果按 `tool_use_id` 挂回；`sessions.js` 用同一个渲染器重建（默认收起，标签用步数代替耗时）。非写作会话的 payload 完全不变。
- **`write-progress` 并入工具行**：写正文那行右端直接显示「起草中 · N 字」，结束时定格耗时；不再另起一行进度。

**理由**：写作 agent 一轮可达 40 轮 ReAct，期间没有任何可见反馈时「在干活」和「卡死」不可区分；但逐条常驻显示会把对话流变成日志。参照 workbuddy 的三层折叠，默认只留最终回答，需要审计时逐层点开。零 token、零前缀缓存影响，纯展示层。

**落点**：`api/routes/chat.py`（`_tool_display` / `_tool_summary` / `_tool_ok`，`tool_start` / `tool_end` 字段）；`reader/js/chat.js`（`initTurnTrace` / `ensureTurnTrace` / `freezeNarration` / `addToolStep` / `finishTurnTrace` / `renderTurnTraceFromSteps`）；`reader/style.css`（`.turn-head` / `.turn-trace` / `.tool-step`）；`api/routes/sessions.py` + `reader/js/sessions.js`（steps 回放）。

### 161. 细致模式：抬证据门槛与预算，不换流水线

**结论**：写作页增加会话级子模式「高效 / 细致」（后端值 `standard | detail`），单章可覆盖。界面用阅读页同款分段药丸，只在空白会话出现，开头对话后固定；之后由 agent 经作者授权切换。细致模式**不新增阶段**，只改三处：

- **证据门槛**：动笔前必须交 `research_brief`（`questions` / `searched` / `gaps`）；细致模式下 `refs` 与 `gaps` 至少一个非空。只验形状，**不设检索次数或素材条数配额**。作者说「这章随便写」时，可以单章降档，或在 `gaps` 里写明降档要求。
- **资源预算**：装配总预算 6000 → 9000；`external_reference` 900 → 2000，`work_docs` / `recent_summaries` / `context_card` 略增。必需块（合同 / 账本 / 上一章结尾 / 上下文卡）的语义不变。
- **自检**：`review` 的上下文带上本章 brief；`review.md` 只用它判断「没查到的 gap 有没有被当成事实写」，不新增评分项，也不把「没用某条素材」当问题。

**决策权边界**（判断「该写进代码还是提示词」的四层）：

| 层 | 归属 | 判据 |
|---|---|---|
| 不变量 / 状态机 | 代码 | 数据模型的前提；模型不该有机会绕过 |
| 事实与成本 | 代码呈现，模型读取 | 模型缺的是现场，不是指令 |
| 判断与取舍 | 模型 | 没有唯一答案（查什么、用哪条、怎么写） |
| 承诺与声明 | 模型填写，代码验形状 | 无法验证「想得够不够」，可以要求「交代清楚」 |

模式切换也按这条线：**模式归作者**。`writing_set_mode(mode, chapter_index, authorized, remember)` 在未获授权时只返回 `needs_authorization`；作者本轮明确同意后传 `authorized=true`，说「以后你决定」才传 `remember=true`（且必须同时 `authorized=true`）。持久授权存 `sessions.auto_mode_switch`，会话模式存 `sessions.writing_mode`（迁移 15）；单章覆盖存 `chapters.writing_mode`（writing.db 迁移 14，空串 = 继承）。brief 存 `chapter_briefs`，跟这一稿一起入库，**不进写作 git**。

**理由**：数量配额会诱导凑数（「至少找 5 条」比「说清为什么不需要」更容易被伪造），但声明的形状可以机械校验；brief 把「有没有想」变成「能不能交代」，而不规定「必须怎么想」。细致模式若做成「调研 → 提纲 → 初稿 → 二稿」，就是把认知流程也写死，正好是这一轮要避免的手铐；只抬证据门槛与预算，模型仍可一句话交差（室内对话，无外部素材），也可以认真跑五轮。

**不做的**：不强制检索轮次 / refs 条数；不把细致写成阶段流水线；不让模型无授权切模式；不判 brief 的质量；brief 不进 git（过程元数据不是正典）。

**落点**：`storage/db_session.py`（迁移 15、`SessionRow` 两列）；`storage/writing_db.py`（迁移 14：`chapters.writing_mode` + `chapter_briefs`）；`writegraph/budget.py`（`MODE_PROFILES` / `profile_for`）；`services/writing_service.py`（`agent_prompt(mode=)`、`effective_writing_mode`、`validate_research_brief`、`stream_chapter(mode/brief)`、review 带上 brief）；`writegraph/chat_tools.py`（`writing_set_mode`、draft 的 `research_brief`）；`api/routes/chat.py`（会话模式读写、ctx）；`prompts/writing/mode_detail.md` + `agent.md` + `review.md`；`reader/index.html` + `reader/js/mode.js`（同款分段药丸、滑动药丸、空白会话可见）、`reader/js/state.js`（`S.writingMode`）、`reader/js/chat.js`（空白会话才发 `writing_mode`）、`reader/js/sessions.js`（加载会话同步已冻结模式）；测试 `scripts/test_writing_mode.py`（已进 `check_all`）。

### 162. 古早批注按原文找回位置；删除只有一个入口

**结论**：v16 之前存的批注没有 `cfi_range`，正文里既没有角标也没有下划线，只能在列表里看到。现在改为**每次加载按原文现算 CFI**：section 渲染出来后，在它的文本节点里找 `selected_text`（有 `context_before/after` 时优先认上下文对得上的那处，同文多处又没上下文就不猜），用 `contents.cfiFromRange(range)` 得到一个 CFI，之后就走和新批注完全相同的一条路。

- **不写回数据库**：CFI 是这条路径上现算出的坐标，`selected_text` 才是真源。回写意味着一次误判就被固化；不回写则每次加载重扫一遍（一段文本，代价可忽略），书重导入改过原文时自然找不到、也不会留下错误坐标。
- **解析结果进同一张表**：解析出的 CFI 直接进 `_commentGroups` / `_collections`，所以预览下划线、气泡、删除、`bcAnnotationDeleted` 全都不用分叉。
- **删除只有一条路**：`DELETE /api/annotations/{id}`，入口三处（阅读页气泡 / 笔记页 / 浮窗）都先 `confirm` 再走 `bcAnnotationDeleted(id)` 同步正文层的线与角标——不重新加载也能立刻看到标记消失。
- **卡片上的删除按钮走捕获阶段**：笔记卡片本身挂着「点击跳转原文」，`document` 上的捕获监听先拦下这一下并 `stopPropagation`，否则删完顺手把书翻走。

**理由**：古早数据是既成事实，改库风险大于收益；而「按原文找位置」本来就是这批记录当初唯一的定位手段（`compute_annotation_offsets` 算的就是这个），只是渲染侧一直没用上。

**落点**：`reader/annotations.js`（`_legacyAnns` / `_findTextRange` / `_resolveLegacyInContents` / `window.bcAnnotationDeleted` / `deleteComment` 的确认）；`reader/notes-panel.js`（`deleteAnnotation` / `.note-del` 按钮与捕获拦截）；`reader/style.css`（`.note-del`）。

### 163. 收藏的两种呈现：框选与下划线

**结论**：收藏在正文里可以有两种呈现——`underline`（默认，贴着每行文字画线）和 `box`（框选，整次选区只画**一个**框，跨段也把几段一起圈进去）。样式入口在浮动条「收藏」按钮上：鼠标悬停时向上弹出菜单（框选 / 下划线），点「收藏」本体仍是一键下划线。

- **两种呈现都画在自绘层**：在 view 容器上叠一层自己的 svg（容器 `position:relative`、iframe 内部不滚动，行矩形减去 iframe 在容器里的偏移就是 svg 坐标）。不用 epub.js 的标注层有两个实证理由：① 跨段选区时 Chrome 的 `Range.getClientRects()` 会退化成「整段块框」，它的 `Underline` 逐行照画，一条 460 字的批注预览线全是顶格的黑线；② 它的 `annotations.add` 只替换账本、不摘旧 mark，重放（每次 `rendered` + 5 轮退避）会把同一个 view 叠出一摞同坐标 `<g>`，线越刷越粗。自绘整层清掉重画，两个问题一起消失。
- **框选**：行矩形取并集，画一个圆角矩形——跨三段也只一个。**下划线**：`_lineRectsOfRange()` 把跨块的 range 按文本节点切开、逐个取 `getClientRects()`，拿到真正贴字的行框，每条画一条线（短段落不再被撑到整栏）。
- **重画时机**：section `rendered`、view 重建（iframe 换了就换 svg）、iframe 尺寸变化（`ResizeObserver`，字号/版心/窗口都会走到）。账本依旧是 `_collections` + `_underlineCfi`（批注预览线），删改后整层重画，不另存一套状态。
- **命中区**：框只有边框附近可点（透明宽描边 + `pointer-events: stroke`），框内正文保持可选中；下划线在每条线下叠一条 16px 透明命中线，点线同样进编辑态浮动条。可见元素本身不吃指针。
- **样式存 `annotations.style`**（v16 已有列），只认 `underline | box`；空值按下划线渲染，历史数据不迁移。同一段换样式时账本覆盖，重画自然就换过来了。
- **菜单挂成浮动条的子节点**：`mouseleave` 按 DOM 祖先判定，指针从按钮移到菜单上不会触发收起，省掉一套 fixed 浮层同步坐标的逻辑；菜单对准「收藏」按钮而不是浮条正中。弹出用 WAAPI（170ms，上浮 6px + 缩放 .96→1 + 淡入），`prefers-reduced-motion` 直接落位。触屏没有 hover：点「收藏」先出菜单，再点款式才落库。
- **夜间换色**：`--bc-collect-stroke` 白天深棕、夜间提亮，框与下划线共用（深棕压在深色正文上等于没有）。
- **正文屏蔽浏览器原生菜单**：Edge 的 mini menu（复制 / 搜索 / 更多操作 / 隐藏菜单）会在选区上直接弹出来，正好盖住浮动条。正文的 `contextmenu` 一律 `preventDefault`——native 走每个 iframe 自己的 document（`_suppressNativeMenu`，与「点空白收条」同一处挂载），chunk 版走主文档对 `#bookPage / #bookPageNative` 的捕获监听。聊天、笔记、写作页的右键不受影响；右键动作由浮动条接管（收藏 / 批注 / 引用 / 复制）。

**理由**：框选在中文阅读里是「这一段被记住了」，下划线是「这句话被记住了」——两种粒度不同的记忆不该共用一个符号。自绘一层比改 epub.js 分叉便宜，且不碰重放机制（点击、删除、`bcAnnotationDeleted` 全走同一本账）。

**落点**：`reader/annotations.js`（`_annStyle` / `_boxPaneFor` / `_redrawMarksInContents` / `_drawBoxRect` / `_lineRectsOfRange` / `_drawUnderlineLines` / `_showAnnotationUnderline` / `createCollection(style)` / `_wireStylePop` / `_stylePopOpen` / `_popAnimate`）；`reader/style.css`（`.bc-box-pane` / `.bc-box` / `.bc-box-hit` / `.bc-line-hit` / `.bc-style-pop`、`--bc-collect-*`）；`api/routes/annotations.py`（`style` 归一为 `underline|box`）。

### 164. 素材进对话：先挂附件，按下发送才走

**结论**：素材卡的「添加到会话」不再直接发消息，而是在输入框上方挂一枚可移除的胶囊（文件图标 + 卡标题 + ×）。可以一次挂多张；按下发送时随这一条消息一起送出，送出即清空——附件与输入框同生命周期。同一张重复挂（id 或路径相同）只留一份；只挂素材、不打字也允许发送。

- **传出的是事实，不是流程**：进消息的是一段 `[本轮附加素材]` 块（id / 标题 / 分类 / 路径，多张分段落），怎么读、要不要 `promote`、用没用上要不要记 `use`，交给写作提示词里的材料规则；UI 不写指令。
- **不用输入框里的文本承载附件**：手改输入框很容易把结构化坐标删坏，也会和作者自己要打的字抢位置；托盘是独立选择，× 即撤销。
- **卡片抬头里的身份 / 会话 id 渲染成复制按钮**（悬停「复制素材id / 复制会话id」），点一下进剪贴板。只装饰第一个 `## 原文` 之前的引用块；文件本身仍是纯 Markdown，改名、换分类、脚本读取都不受影响。
- **气泡里留一行附件名**：托盘发完就空，回看这一轮带了什么只剩气泡那一行。
- **编辑态不提供「添加到会话」**：此刻磁盘上还是旧版本，发出去的引用会错位。
- **胶囊只露前四个字**（超出加「…」），完整标题与路径放悬停提示：卡片标题动辄十几字，全显示会把输入框上方铺满。
- **素材卡抬头只留标题**：分类 / 标签 / 采集时间在卡片正文里已经有了；「添加到会话」「编辑」收成一组靠右、间距 6px，不再被 meta 推到正文中间。

**理由**：一键直接发一轮，等于把「我想先说说要什么」挤掉，一次误点还要付一轮 API 成本；挂附件是编辑动作，发送才是提交动作。胶囊比输入框文本更像「临时负载」，也更接近作者对文件标签的直觉。

**落点**：`reader/index.html`（`#writeDocAddBtn`、`#attachTray`）；`reader/js/writing.js`（`decorateMaterialHead` / `copyChipValue` / `addCardToSession`、`renderLibraryCard` 显示按钮）；`reader/js/chat.js`（`attachedMaterials` / `attachMaterial` / `renderAttachTray` / `materialAttachBlock`，`sendMessage` 里拼消息与清空）；`reader/style.css`（`.attach-tray` / `.attach-chip` / `.mat-copy` / `.bubble-attach`）。

### 165. 收录为素材：原始摘句落待归类，纸团飞向写作导航

**结论**：阅读页选中文字后的浮动条新增「收录为素材」。点它把**选中的逐字原文**直接存进全局素材库的 `待归类/`，文件名 `《书名》-YYYYMMDD-HHMMSS.md`；同时一颗纸团从选区内随机一点沿抛物线飞向左侧写作导航图标，落地后纸团消失、图标播放被击中的缩放 + 外圈扩散。加工（分类、摘录、说明）不在这一步做。

- **待归类卡与加工卡分两条落盘路径**：`mat.intake()` 是加工卡（`<hash>-<标题>.md`，同原文同出处去重）；新增 `mat.intake_raw()` 按书名 + 时间戳命名、不去重（同一段文字不同时间收两次就是两份原料，归并留给作者）。抬头仍由 `card_markdown()` 生成，解析 / 列表 / 回收站 / 审计照常工作。
- **后端查书名，前端不背标题**：前端只传 `book_id + excerpt + cfi_range`，服务端按 `books.id` 取书名；`chapter_index / chunk_index` 只在 chunk 模式传（native 模式的 `S.currentChapter` 未必跟选区走，宁缺勿错）。身份只用「原文 + 书/章/块」；CFI 存在 `> 定位：` 抬头行里只做回查线索，不参与身份（卡头存不下它，audit 重算会永远对不上）。加工时见决策 167。
- **动画是确认感，不阻塞落盘**：请求先发出，飞行同时进行；纸团用 `position:fixed` + WAAPI 二次贝塞尔采样（26 帧，中点上抬 `max(60, min(220, 距离×0.45))`），末 10% 淡出，落地后移除节点并给 `#navWrite` 加 `.nav-hit`。`prefers-reduced-motion` 下不起飞，图标也不跳。
- **起点在选区内随机**：取 `range.getClientRects()` 里落在视口内的行框，随机一行、随机一点，再按 iframe 的 `getBoundingClientRect()` 换成主文档视口坐标。
- **失败不打扰**：接口失败只在控制台报错，图标动画照常收尾（作者至少知道点击被接收了）。

**理由**：从阅读页收集原料是「先囤后用」，此刻还没有分类语境，任何自动归类都是猜；统一先进 `待归类` 是最便宜的回退位。纸团是一次性的空间叙述——素材去了写作页，而不是「保存成功」四个字。命名用书名 + 时间戳让人在文件系统里也认得出原料来源，不依赖卡片抬头。

**落点**：`writegraph/materials.py`（`intake_raw` / `book_title`）；`services/writing_service.py`（`materials_intake_raw`）；`api/routes/writing.py` + `api_server.py`（`POST /api/writing/materials/intake`）；`reader/annotations.js`（`intakeMaterial` / `_randomPointInSelection` / `_spawnPaperBall` / `_flyPaperBall` / `_navWriteHit`）；`reader/index.html`（`#navWrite`）；`reader/style.css`（`.bc-paper-ball` / `#navWrite.nav-hit`）。

### 166. 笔记页：服务端查询 + 分页，删除给 5 秒撤销

**结论**：笔记页的过滤、排序、分页全部交给服务端（`GET /api/annotations` 加 `q` / `color` / `sort` / `limit` / `offset`，响应补 `total`），前端只负责累积已加载的页与渲染；删除不再弹 `confirm`，卡片先隐藏、5 秒后才真正 `DELETE`，这段时间里可以从 toast 上撤销。

- **为什么不能再「拉 500 条前端过滤」**：超过 500 条会静默截断，用户永远看不到更早的笔记；搜索每次敲字还要把全库重拉一遍。服务端查询把 `COUNT(*)` 与当页行一起返回，页面顶部显示「共 N 条 · 已显示 M」，截断从隐性变成显性。
- **排序键只认常量表**：`_ANNOTATION_SORTS` + 书名子查询（取 `stable_book_id` 最近一次导入的书名，避免重导产生的多行把批注复制成 N 份）；排序末尾统一用 `id` 兜底，否则相同时间戳的行翻页会重复或漏行。
- **LIKE 要转义**：用户输入的 `%` / `_` 按字面匹配（`ESCAPE '\'`），否则一个 `%` 就把全库捞出来。
- **分组是显示层，不是查询层**：书 → 章的分组只在按书 / 按章排序时用；切到时间 / 字数排序就回平铺——全局时间线被书分组打断会读不出「最近写了什么」。
- **删除的撤销窗口**：卡片立刻隐藏，`DELETE` 真正发出前都可以撤回；撤销就清掉定时器，从头到尾不碰库，正文层的角标与下划线等落库后由 `bcAnnotationDeleted` 同步收掉。跨页签/筛选重画时会把待删卡片重新藏起来，避免「删了又回来」。
- **导出读数据不读 DOM**：分页之后 DOM 只有当前页，读 DOM 会静默导出半截；导出按当前筛选条件向服务端要全量，再按书 → 章组结构、带上时间。
- **并发用序号而不是丢请求**：搜索的重新加载不能被在飞的旧请求挡掉，响应按 `seq` 丢弃过期的那份；只有「加载更多」需要防连点。
- **老进程兜底**：服务还没重启时接口不认新参数、也不回 `total`，前端检测到就退回老办法（一次拉 500 + 前端过滤排序）。这是过渡代码，重启后不再走到。
- **颜色不再是笔记的维度**：正文层早已不按 `annotations.color` 着色（`annotations.js` 里零引用），所以「全部颜色」筛选、编辑器里的六色选择、列表色点一并移除；`color` 列与接口参数保留不动（存量数据不迁，读者不再被要求做无意义的分类）。
- **全屏两栏 + 书籍泳道**：笔记页不再是居中浮着的纸面卡片，改成整页 grid：左栏书籍泳道（封面 + 书名 + 当前页签条数），「全部书籍」固定在栏顶不参与滚动，其余泳道直接复用书架页的 `sortBooks`（同一份比较器、同一个 `bc_shelf_sort`），点哪本就把列表收窄到哪本；泳道只列当前页签下有内容的书，已选中的书即使 0 条也保留一行（否则选中态会凭空消失）；选中单本时列表不再重复书名组头；正文内容宽上限 980px，窄屏（≤820px）左栏折成顶部横排封面。每书条数走 `GET /api/annotations?type=…&counts=1`（`count_annotations_by_book` 只做 GROUP BY），不拉批注行。
- **类型开关是导航的第一层**：批注 / 收藏从正文页头移到左栏顶部，做成两段式开关——先选看什么，再选看哪本书；正文页头因此只剩两行：第一行大标题「阅读历程」+ 导出，第二行排序靠左、搜索靠右。搜索入口收成一枚约 560px 的窄框（不再铺满整行），总数「共 N 条 · 已显示 M」跟在搜索框同一组里（搜索后它是唯一能看出筛掉多少的指标）。
- **两个页签共用一套排序**：批注和收藏都能按 A→Z / 最新 / 长→短 / 章节排，不再让收藏固定按书→章、把排序按钮行藏起来；收藏是平铺卡片，排序只改顺序，不做书→章分组。章节排序补了方向：第一次点保持原来的升序（章节↑），再点一次翻成章节↓；SQL 以书名为第一键保持不变、章与块向内翻转（`chapter` 旧键保留为升序，兼容老调用方）。笔记列表的分组顺序跟着方向走——书组按 A→Z 或 Z→A，章组与块按 ↑/↓；以前 Z→A 与章节方向在分组渲染里会被重新排回升序，这次一并修正。
- **书籍排序菜单与书架共用一份偏好**：左栏「书籍 + 当前排序」的触发器打开五项菜单（导入时间 / 书名 / 作家 / 最近打开 / 自定义）；切 key 或对激活项再点一次翻方向，走的是书架页同一套 `setSort` 语义与同一个 `bc_shelf_sort`，两页永远同序。**自定义除外**：手工序列固定正序，激活后再点不翻方向，也不画方向箭头；tooltip 写「整理请去书架页」。菜单里不提供「自定义整理」的 grip 入口（拖书排序是书架页的动作），这里选自定义只读已有 `sort_order`。菜单只原地更新激活态与方向箭头、不重建按钮 DOM——重建会在 click 冒泡途中把被点的按钮摘出文档，window 的「点外面收起」随后就认不出它，表现为点一下选项菜单自己关了。
- **阅读页浮窗是「本书笔记」，不是跨书列表**：按钮 title 与浮窗抬头都写「本书」。查询先走 `GET /api/annotations?stable_book_id=…&type=note` 并前端再按稳定书号筛一遍；`?type=` 与 `stable_book_id` 的组合在旧进程里曾经忽略稳定书号，把全库笔记倒进浮窗（参考书A里冒出别的书的批注）——响应里一旦出现别的书，就退到 `?stable_book_id=…`（不带 `type`）的 book-scoped 分支重取，再筛 `note` / `both`。浮窗请求带序号，每次 `await` 后都校验 `S.currentBook` 仍是发起时那本；换书时浮窗开着就自动刷新，上一本书的在途响应不会写进新书。


**理由**：笔记页是「回头整理」的地方，条目只会越积越多；把过滤和分页放在读取端，才能让人翻到几个月前的那条。删除是这里唯一的破坏性动作，5 秒撤销比每次弹窗确认更省事，也更安全。

**落点**：`storage/db.py`（`query_annotations` 的 `chapter` / `chapter-asc` / `chapter-desc` 分支 / `get_chapter_titles` / `count_annotations_by_book` / `_ANNOTATION_SORTS` / `_BOOK_TITLE_SQL`）；`api/routes/annotations.py`（`handle_list_annotations` 的 type 分支 + `counts=1` 汇总）；`reader/notes-panel.js`（`loadAnnotationPage` / `renderNotesPageList` / `renderGroupedNotes` / `renderBookRail` / `selectNotesBook` / `syncNotesTypeSwitch` / `updateNotesBookSortUI` / `setNotesBookSort` / `setNotesSort` / `updateSortButtons` / `legacyFilterSort` / `deleteAnnotation` / `commitDelete` / `exportNotes`）；`reader/js/shelf.js`（`SORT_KEYS` / `SORT_LABELS` / `setSort` 与笔记页共用）；`reader/index.html`（`#notesRail` / `.notes-type-switch` / `#notesBookSortWrap` / `#notesLaneAll` / `#notesRailList` / `#notesSortRow` / `#notesTotal`）；`reader/style.css`（`.notes-page` 两栏 grid / `.notes-rail*` / `.notes-type-*` / `.notes-booksort-*` / `.notes-lane*` / `.notes-page-toolbar` / `.notes-empty-*` / `.notes-more` / `.notes-toast`）。

### 167. 待归类整理：同一张卡的状态迁移，页面只出建议气泡

**结论**：阅读页收进 `待归类` 的待归类卡，加工时**只补四个字段**（标题、分类、标签、一句话说明）——原文逐字节不动、身份不变、文件迁出 `待归类`。触发只走写作对话：空项目的空白会话在输入框上方挂一颗「待发送」气泡，点一下等于替作者发出整理请求，agent 先列提案、作者确认后才逐张 `cook`；不做页面加工表单。

- **待归类判据不靠目录**：有 `> 加工：` → 已加工卡，无论它在哪；`> 状态：待归类` → 待归类卡（旧标记 `> 状态：生肉` 仍兼容）；兼容决策 165 的旧卡：在 `待归类` 且文件名是 `《书名》-时间戳` → 待归类卡。加工后文件名是 `<id>-<标题>`，不会误判；作者拿不准分类、已加工卡留在 `待归类` 时也不会被当成待加工。
- **cook 是状态迁移，不是重收**：以 `## 原文` 切分，头部重写，正文整段原样保留；`> 收录 / 指令 / 定位 / 采集` 跟着走，末尾追加 `> 加工：<时间>`；新文件 `<分类>/<身份>-<标题>.md`，写成功才删旧文件（删不掉就回滚新文件，绝不留下两张同 id 的卡）。作者手工先写过 `## 说明` 时：给新说明就替换，没给就原样保留。
- **身份规范化**：旧版待归类卡的身份曾把 CFI 算进哈希；cook 时按「原文 + 书/章/块」重算，抬头里的旧 id 一并换掉（待归类卡没有消费连线，换身份安全）。
- **重复只报告**：同原文 + 同出处已有已加工卡时 `cook` 返回 `exists: true` 与 `existing`，不覆盖、不合并；`pending` 的每张卡也带 `duplicate_of`，由作者决定怎么处理。
- **建议气泡只做侦测**：`materials_list` 带回 `pending_count`，页面在「写作页 + 空项目 + 空白会话 + 有待加工」时显示 `#writeCookSuggest`，文案带张数；点击只是把「整理一下」的请求发进对话，不自动跑。`[hidden]` 必须显式写 `display:none`（作者 CSS 的 `display:flex` 会盖掉 UA 默认规则）；会话开口、切页、选作品都会重新求值。
- **收录成功即刷新素材库**：阅读页 `intakeMaterial` 拿到 `path` 后调用 `WritingUI.refreshLibrary()`（只走 `loadLibrary`，不碰作品、章节与版本现场）。切回写作页时 `open()` 在「作品没变」那条分支会早退、不刷新；靠这次刷新，左栏「素材库 → 待归类」与待加工数才不会停在旧状态。
- **不自动加工 / 合并 / 拆分**：加工是判断动作，四个字段只是最小可检索集；分类拿不准就留在 `待归类`。

**理由**：从阅读页收原料时没有分类语境，加工时必须有人做取舍；把状态迁移与身份绑定，出处和消费连线都不会断。气泡把「有待办」摆到输入框上方，但真正动手仍由作者点火。

**落点**：`writegraph/materials.py`（`RAW_STATE` / `COOK_MARK` / `LOCATION_MARK`、`is_raw_card` / `pending_cards` / `cook`、`intake_raw` 的身份与 `> 定位：` 行）；`services/writing_service.py`（`materials_pending` / `materials_cook` / `materials_intake_raw`、`materials_list.pending_count`）；`writegraph/chat_tools.py`（`pending` / `cook` action）；`prompts/writing/agent.md`（待归类整理流程）；`reader/index.html`（`#writeCookSuggest`）；`reader/js/writing.js`（`refreshLibrary` / `syncCookSuggest` / `runCookSuggest`）；`reader/annotations.js`（`intakeMaterial` 收录成功后 `refreshLibrary`）；`reader/js/mode.js`（`updateWritingModePrelude` 挂钩）；`reader/style.css`（`.write-cook-suggest` / `.write-cook-chip`）。

### 168. 写作页 agent 输出里的文件路径可点开

**结论**：写作页的 agent 输出里，`.md` 路径（反引号里、加粗里或裸写）渲染成 `.write-file-link`，点击就在工作区打开该文件。渲染只做形态识别，点击时才解析真实位置：工作区文档 → 素材卡 → 章节；找不到先刷新一次工作台，仍没有就明确报错。阅读页 / 首页不挂链接。

- **只在写作页**：`renderMarkdown` 检查 `_currentTab === 'write'`；路径识别发生在代码块被换成占位符之后，所以 `pre/code` 里的路径保持原样，不会被误标成链接。
- **链接是标记，不是渲染时校验**：路径先替换成 `\u0000FL<n>\u0000` 占位符，最后才还原成 `<a class="write-file-link" data-write-path="…">`，因此不会被加粗/列表/段落规则改写；HTML 先转义，路径不会带进标签结构。
- **边界**：路径前只允许空白或标点，像「见设定/…」这种贴着汉字写的不链接；只认 `.md`，目录不链；只写文件名时按唯一 basename 命中，重名不猜。
- **点击时解析**：`openWriteFileLink` 先查当前 `S.docs` / `S.library`（精确，再唯一 basename）；找不到就 `loadDocs + loadLibrary` 重试一次；再按「第 N 章」匹配章节。工作区文档走 `openDoc`，素材卡走 `openLibraryCard`，都先 `setView('draft')`。
- **为什么不在渲染时校验**：助手可能在**这一轮**刚创建文件，而最终气泡渲染发生在回合末的 `WritingUI.refresh()` 之前；拿旧现场校验会漏掉新文件。把存在性判断挪到点击时，最坏也只是点一下得到「找不到文件」。
- **样式**：复用 accent（夜间自动换色），不另造一套链接蓝；反引号路径保留 `<code>` 字体但去掉背景。

**理由**：写作 agent 的回答里最常见的可操作对象就是文件路径（`设定/人物/人物A.md`、`素材/网络/…`），让人再从左栏找一遍是重复劳动。链接化只加一层标记，不改变正文与渲染语义；真正的文件解析仍由工作台现场负责。

**落点**：`reader/js/chat.js`（`WRITE_FILE_LINK_RE` / `linkWriteFilePaths` / `renderMarkdown` 的占位符还原）；`reader/js/writing.js`（`onWriteFileLinkClick` / `findOpenablePath` / `openWriteFileLink`、`#chatLog` 委托点击）；`reader/writing.css`（`.write-file-link`）。

### 169. 书架自定义排序：直接拖封面，手工序列固定正序

**结论**：自定义排序是一条手工序列（`sort_order` 1→N），不是第六种可翻方向的排序。它永远正序：比较器忽略 `dir`，书架与笔记页都不画方向箭头，激活的自定义项再点不翻方向；旧 `bc_shelf_sort` 里的 custom+desc 读入时归一到 asc。**自定义本身就是可拖视图**：没有独立的「整理模式」、没有完成键、没有额外入口；菜单选中自定义即收起面板，随后鼠标按下封面、移动超过 8px 进入拖动，松手落位自动保存。触屏用 320ms 长按起拖，先滑动则取消并交给页面滚动。

- **为什么取消显式模式**：用户已经选了自定义，再开一次排序面板点「整理」是重复导航；把手机桌面的「长按 → 拖动 → 松手」映射成「按封面 → 拖动 → 松手」，选自定义这一步同时成为进入整理。代价是拖拽判定必须和点击、倾斜、角标、触屏滚动共存，下面逐项拆开。
- **选中即重排**：从别的排序切到自定义时，直接用 `_lastShelfBooks` 的缓存 `sortBooks` 同步重渲染，不再等 `loadShelf`；否则旧排序还在屏幕上、拖拽却已经可用，一拖就会把旧顺序写回。没有缓存时才回退 `loadShelf`。
- **点击与拖动**：鼠标阈值 8px，短点仍走 `openBookFromShelf`；拖动松手后 350ms 内的 click 在 capture 阶段被吞掉，防止误开书。角标 `.book-actions` 不参与起拖，按钮点击照常。
- **触屏**：`pointerdown` 起 320ms 长按计时；移动超过阈值先取消（视为滚动）；长按成立后用非 passive `touchmove` 阻断页面滚动；`pointercancel` / 页面隐藏 / 窗口 resize 都取消拖拽。
- **拖动期间才降级**：JS 的 `_drag` 闸门停掉倾斜，CSS `.dragging-active` 放开离屏行 `content-visibility` 并隐藏角标，`body.shelf-dragging` 禁选词；平常的悬停抬升、角标和入场动画不受影响。
- **落位与动画**：拖动中 DOM 不动，只移动插入位指示条；松手后按 `data-id` 重渲染 + FLIP；`_suppressEnterAnim` 只抑制这次落位重渲染的入场动画，切排序 / 重载时恢复。
- **换排序 / 重载**：`setSort` 先 `endDrag()`；`loadShelf` 在拖动中直接 return，避免重建 DOM 把正在拖的节点换掉。
- **方向语义**：`sortBooks` 的 custom 分支不乘 `sign`；`setSort` 对激活的 custom 直接返回；`loadShelfSort` 归一化旧值；`updateShelfSortUI` / `updateNotesBookSortUI` 不给 custom 画 chevron，笔记页 tooltip 改成「自定义顺序固定，整理请去书架页」。
- **触发器的提示**：当前排序是自定义时，排序触发器的 tooltip 改成「自定义顺序：拖动封面调整」，不额外增加常驻按钮或提示条。

**理由**：用户的原话是「我都打开自定义了，还得再开一遍排序按钮点击调整自定义顺序」——入口问题的本质不是按钮太小，而是重复导航；把「整理」做成第二个动作只是把重复导航做大。直接拖封面让「选自定义」同时成为进入整理，和手机桌面的长按 / 拖动 / 松手同构；触屏保留长按，是为了不牺牲书架滚动。

**落点**：`reader/index.html`（删除 `#shelfReorderBar`、`.sort-arrange`、`.sort-panel-divider`）；`reader/style.css`（`.custom-order` / `.dragging-active` / `body.shelf-dragging` / `.no-enter-anim`）；`reader/js/shelf.js`（`setSort` / `updateShelfSortUI` / `openBookFromShelf` / `initShelfReorder` / `startDrag` / `onReorderMove` / `onReorderUp` / `commitDrag` / `endDrag` / `renderShelfRows` / `loadShelf`）；`reader/notes-panel.js`（`updateNotesBookSortUI`）。

### 171. 笔记/收藏变更日志：事件表 + 只读工具

**结论**：`annotation_events`（books.db migration 25）是笔记/收藏的 append-only 变更日志，记录 `create` / `update` / `delete`。创建、修改、删除三个 API handler 在动作完成后各写一笔；查询收口到 `BookDB.list_annotation_events()`，agent 通过只读工具 `annotation_event_log`（`library_query`，DEFERRED）读取。

- **表字段**：`annotation_id` / `stable_book_id` / `book_id` / `book_title`（快照）/ `event_type` / `annotation_type` / `style` / `selected_text` / `note_text` / `changed_fields`（JSON 数组）/ `chapter_index` / `chunk_index` / `time_created`。不建外键：批注删了事件还要在；书名存快照：书后来被删日志仍可读。
- **只记真正的变化**：更新事件对比 before/after，`changed_fields` 只列实际变了的字段；同样的值重复保存不产生事件。
- **删除保留最终快照**：`note_text` / `selected_text` 存全文（工具展示时截断），所以「删掉的那条写了什么」仍答得出来。
- **写入 best-effort**：事件插入失败只记 warning，绝不阻断用户的批注动作。
- **历史回填**：`scripts/backfill_annotation_events.py` 给现有批注按 `time_created` 补 `create`、`time_updated > time_created` 补 `update`（快照是当前值）；已经物理删除的批注补不回来。
- **工具**：动作 / 类型（收藏/笔记）/ `book_id` / `stable_book_id` / 关键词（原文/笔记/书名）/ 分页；输出动作、书名、章块、原文与笔记预览。

**理由**：

- `annotations` 只存最终态：更新覆盖旧值、删除是物理 `DELETE`，前端 5 秒撤销后真发请求。光加查询工具只能看到「现在有什么」，回答不了「昨天改/删了哪条」。
- 不复用 `annotation_search`：它的语义是「按内容找当前批注」，空查询没有意义；动作流与内容检索是两个查询维度，混在一个 schema 里会让模型难以判断该用哪个。
- 不用 SQLite trigger：`orphan_annotations_for_book` / `relink_annotation` 是系统动作，触发会制造大量噪声；用户动作只在三个 API handler 发生，显式写入更清楚，也方便 best-effort 处理。
- 与决策 170 同构：书库的 `import_log`、笔记的 `annotation_events`、写作的 git 各自是真相源，不为「统一日志」再建一张跨域表（写作页工具集也看不到 library 工具）。

**落点**：`storage/models.py`（DDL + `AnnotationEventRow`）；`storage/db.py`（migration 25、`get_annotation` / `insert_annotation_event` / `list_annotation_events`）；`services/annotation_events.py`（写入 helper）；`api/routes/annotations.py`（三处调用）；`tools/library.py`（`annotation_event_log`）；`scripts/backfill_annotation_events.py`；`scripts/test_annotation_event_log.py`。

### 172. Agent 设置页：左栏身份组 + 折叠外观 + 独立定义文稿 + 头像

**结论**：主题页升级成 Agent 设置页。设置页是左右等宽等高的双台：左设置台从「个性化」顶带开始，顶部是始终可见的「身份」组（agent 行 + 「我」行，放头像、称呼、SOUL 状态与「个性化定义」），下方是「外观」折叠分段（sunken 底 + accent 顶带）；右实时预览台是 raised 桌面 + 限宽纸页，笔记为浮窗叠在真实书页上。SOUL.md 走独立的文稿视图（单栏稿纸编辑，显式保存），不再带预览页。

- **称呼与人格分账**：`agent_name` 存在 `settings.json`，改一次即同步聊天标题、加载占位、预览、语音试听；系统提示词由 `load_persona` 在 SOUL 末尾追加 `## 称呼` 段（“你对外叫「X」”）。SOUL.md 仍只负责人格、文风与边界；改名不改写手稿文件——读取时（以及改名成功后）只把库存身份句和 `# <旧称呼> — 灵魂` 标题行归一成当前称呼（提示词、左栏身份组、编辑器同一口径），正文一个字节不动，用户显式保存才落盘。名字旁边的铅笔是真正的按钮，点它聚焦并全选输入框（避免看起来像图标却点不动）。
- **空名只在退出编辑时回退**：编辑过程中允许暂时为空（全选删除、准备输入新名不会被 700ms 防抖中途重置）；失焦、Tab 或回车提交时仍为空才恢复当前已保存的名字（提示「已恢复原名」），非空的新值照常覆盖。
- **默认身份也带名字**：`DEFAULT_IDENTITY_TEMPLATE` 用 `{name}` 占位；没有 SOUL.md 时按当前称呼生成出厂人格，`save_default_soul` 同样用模板。
- **`## 称呼` 而非 `# 称呼`**：role-play 的 `_extract_soul_boundary` 只截 `## 边界` 到下一个 `## ` 为止，称呼段不会混进扮演模式的边界兜底。
- **折叠与预览联动**：点段头即切到该段并把右侧预览同步（阅读 / 交互 / 笔记）；预览工具栏不再放胶囊页签，左侧分段是唯一选择器。段头显示当前值摘要（如 `18px · 楷体 · 54em`），收起时也不丢信息。
- **折叠是高度过渡，不是 display:none**：段体用 `grid-template-rows: 0fr → 1fr` 展开/收起（250ms ease-out），内容随高度做轻微淡入；收起后的表单控件挂 `inert`，不会被 Tab 焦点摸到。
- **双台等高，色块不对称配重**：左右两栏等宽等高、同圆角同边框；左设置台用 8% accent 调过的 `--bg-sunken` 底 + 28% accent 顶带，右预览台用 `--bg-raised` 作桌面，纸页限宽 640px、四周 20px 留白居中。右侧深色纸页仍是视觉重心，但左台有了同等体量，不再「左边轻、右边一块深色」。
- **身份是左栏第一组，不是外观分段**：agent 与「我」两行放在左栏顶带下、始终展开，先回答「谁在说话」，再往下才是外观分段。身份行不切换右侧预览——它和阅读/交互/笔记不是同一层，若做成会切预览的折叠段，点身份却换了预览是误导；把原先两条全宽身份带收回左栏后，预览台拿回整页高度，左栏也不再是「外观一个面板孤零零地贴在上方」。
- **预览读真实现场，不画样张**：阅读取 `S.currentBook || bc_view.bookId`，经 `/api/books` 的 `last_chapter/last_chunk` + `/chunk`（不传 `record=1`）渲染上次读到的正文；交互先读 `#chatLog` 的最近四回合，空则按 `S.currentSessionId || bc_view.sessionId` 拉 `/api/sessions/<id>`（再退到最近的非写作会话）；笔记按书号拉 `type=note` 的真实批注，按章排序后装进真浮窗的 `notes-mini-panel` 标记（静态定位、无删除/关闭），空态仍保留真浮窗标题。三块都在切页/切段时刷新，请求带序号，旧响应不覆盖新现场。
- **笔记预览是浮窗叠真实书页**：同一本书的阅读正文（复用阅读预览的正文缓存，没有就单块读取）铺成与阅读页同宽同内边距的底图，加 68% sunken 薄纱 + 1px 模糊压后；真浮窗按 340×420 的真实尺寸摆在右下角（32px 边距），滚动条在预览里隐藏、仍可滚。没有书/空态时回到居中，手机（≤600px）隐藏底图、只留居中浮窗。
- **预览只读**：不碰 `touch_book_opened`（不读 `/context`）、不写阅读进度（chunk 不带 `record`）、不写会话/批注。预览不替代阅读页，只回答“现在长什么样”。
- **笔记字号以浮窗为基准**：`--t-notes-font-size` 落在 `.notes-mini-panel`，卡片正文/引文/元信息用 em 跟随（默认 13px 时视觉不变）；否则滑杆只改容器、正文永远写死 `--fs-secondary`。
- **两层边框**：右台只留外框 + 纸页（或浮窗）本身；`preview-stage` 不画中间 border，用 raised 桌面与 20px 留白把纸页托起，纸页沿用真实阅读页的 24/32 内边距、纹理与轻阴影。
- **SOUL 编辑显式保存**：不跟主题一起自动保存；有未保存修改时切走会确认，关闭页签有 `beforeunload` 兜底；`Ctrl/Cmd+S` 直接保存。文稿视图只留稿纸，不再渲染 Markdown 预览。
- **保存前必备份、写入原子化**：`PUT /api/agent/soul` 先把旧文件拷到 `data/backups/soul/SOUL-<时间>.md`（保留最近 20 份），再 `os.replace` 临时文件；内容相同不备份也不写盘。恢复出厂要求 `confirm=true`，同样先备份。
- **空稿拒绝**：空白 SOUL 返回 400，避免下一轮提示词悄悄退回出厂人格；想恢复出厂必须走显式按钮。
- **编辑器提示**：字数、`## 边界` 缺失提示（扮演模式会走兜底边界）、超过 6000 字标记偏长（SOUL 每轮都进系统提示）。
- **头像默认没有**：身份带用虚线圆 + 上传图标作占位；上传后存 `data/agent/avatar.<ext>`，`GET/POST/DELETE /api/agent/avatar`。前端先居中裁方、缩到 512px JPEG 再上传；后端按魔数识别 PNG/JPEG/GIF/WebP，2MB 上限，原子替换。聊天里只有上传过头像才显示，且只在普通对话回合的「思考过程」上方出现（扮演模式已有角色头像，不叠加）；头像 URL 带 mtime 版本，换头像即换 URL，不吃旧缓存。
- **设置页文案**：`settings.json` 改为增量合并写回（`save_settings` 不再整份重写），避免丢 `scan_folder` / `graph` 等未建模字段。
- **取色实时预览，松手才落盘**：七个 `<input type=color>` 同时挂 `oninput` 与 `onchange`。拖动取色器时 `onThemeInput` 只把当前值写进 CSS 变量（含阅读器 iframe 的 `applyThemeFromDom`）并刷新色值文字，按帧合并（rAF）不重复写样式；关闭取色器的 `change` 才 `saveSettings` 落盘并重填表单。
- **选中态拆两层，调的时候先给演示**：字色（`selectionColor` / `readerSelectionColor`）与高亮背景（`selectionHl*` / `readerSelectionHl*`：颜色 + 透明度 + 亮度）分开调；背景在 `applySettings` 里合成 `rgba()`（亮度乘 RGB、透明度进 alpha）写进 `--t-selection-bg` / `--t-reader-selection-bg`，主文档 `::selection`、`.book-page ::selection` 与阅读器 iframe 的注入 CSS 同源读取。原生取色器一打开就盖住页面，所以碰「选中字色 / 高亮颜色 / 高亮透明度 / 高亮亮度」任一控件时（pointerdown 或 focus），预览台第一段正文临时加 `.preview-selection-demo` 画成选中态（`onSelectionPreview`）；取色器提交（`change`）或点到别处才撤——**不能挂 blur/pointerup**：原生取色器打开时输入框会失焦，blur 会立刻把演示撤掉，滑块松手即撤则看不到调完的效果。演示层直接读变量，跟手刷新。

**理由**：主题页原本只有“调外观”，身份与灵魂却散落在 SOUL.md 和硬编码文案里；把称呼从人格里拆出来，用户改称呼不必动整篇手稿。SOUL 是会影响每一轮对话的高风险文件，显式保存 + 备份 + 原子写是唯一能接受的方式。折叠外观并不是为了藏设置，而是让左侧从“一直很长的表单”变成可扫读的分段摘要。预览页在 SOUL 单文件编辑里是重复的阅读层，去掉后稿纸能占满版心；头像则把“谁在说话”从文字称呼补成一个可选的身份线索，默认不强行塞一个默认头像。

### 173. 用户资料：自己的头像与称呼

**结论**：Agent 设置页左栏「身份」组的第二行是更轻的「我」：自己的头像（可选，36px）、称呼（可空）、保存状态与一句用途说明。称呼存 `settings.json` 的 `user_name`，头像存 `data/user/avatar.*`；新增 `GET /api/user`、`PUT /api/user/name`、`GET/POST/DELETE /api/user/avatar`。称呼非空时 `load_persona` 末尾追加 `## 用户`（“用户希望被称作「X」”）；空值不注入。

- **用户行在 agent 行下方**：36px 头像 + 「我」胶囊 + 称呼输入 + 键盘可聚焦编辑；放在左栏身份组内、作为第二行，不再占一条全宽身份带。手机端隐藏用途长句，保留头像、称呼与保存状态。
- **头像上传同 agent 口径**：前端居中裁方缩到 512px JPEG；后端按魔数识别 PNG/JPEG/GIF/WebP，2MB 上限，写 `data/user/avatar.<ext>` 并清理旧扩展名；URL 带 mtime 版本。

**理由**：用户自己的身份与 agent 的人格是两个不同的东西，混在 SOUL/USER.md 会让「展示名」污染记忆与人格；放进 `settings.json` 与独立 `data/user` 最轻。聊天只加头像不加姓名标签，保持现有气泡密度；名字通过提示词生效，比在 UI 上贴一个自造 label 更诚实。空名合法是为了不替用户编身份；历史消息补画则解决「先恢复会话、后拿到资料」的时序。

**落点**：`config.py`（`user_name` / load / save_settings）；`persona.py`（`user_display_name` / `_user_directive` / `load_persona`）；`api/routes/user.py`（GET/PUT 名字、头像 GET/POST/DELETE）；`api_server.py`（`/api/user*` 路由）；`reader/index.html`（左栏身份组内的用户行、头像控件、称呼输入）；`reader/style.css`（`.identity-group` / `.identity-user` / `.user-avatar*` / `.user-turn-avatar` / 移动端）；`reader/js/theme.js`（`loadUserProfile` / `refreshUserProfile` / `applyUserName` / `applyUserAvatar` / `saveUserName` / `uploadUserAvatar` / `removeUserAvatar`）；`reader/js/app.js`（启动加载 + 切主题页刷新）；`reader/js/state.js`（`S.userName` / `S.userAvatarUrl`）；`reader/js/chat.js`（用户消息头像、`syncUserAvatars`、`bc:user-avatar`）。

### 175. 书架封面走缩略图 + 主动预热

**结论**：书架 / 笔记泳道 / 「继续阅读」的封面统一请求 `/api/books/{id}/cover?thumb=1`，服务端返回 400px 宽的缩略图；刷新后前端按 6 并发主动预热全部缩略图，不依赖 `loading="lazy"` 的视口触发。

- **缩略图在导入时顺手生成**：`extract_and_save_cover` 写完原图后调 `make_cover_thumb`（Pillow，宽 400px、JPEG q82、progressive），存 `{id}_cover_thumb.<ext>`；Pillow 缺失、原图已 ≤400px 或生成失败时返回 None，端点退回原图，任何情况下不少一张封面。存量封面由 `scripts/backfill_covers.py` 幂等补齐。
- **端点不阻塞事件循环**：改用 `web.FileResponse`（sendfile / 线程读取），不再在协程里同步 `read_bytes`；按 FileResponse 同格式的 etag（`mtime_ns-size`）手写 304 协商，`Cache-Control: private, max-age=604800`。
- **主动预热而不是懒加载**：原生 lazy 要等卡片滚进视口才发请求，快滑永远慢半拍；缩略图全量只有几百 KB，本地 6 并发一轮拉完，之后滚动全是缓存命中（≤150 本，超出部分仍交给 lazy）。

**理由**：原图 500–1700px 宽、最大 800KB，书架显示宽度只有 92–130px；一次刷新要下载 4.4MB 并解码十几倍于显示尺寸的位图，快滑时回填速度必然跟不上。缩略图把下载量降到约 1/5、解码量降到约 1/16，预热把「滚动到来才开始下载」变成「滚动到来时已在内存」。缓存协商保证普通刷新不重读文件。

**落点**：`services/library_service.py`（`COVER_THUMB_WIDTH` / `cover_thumb_path` / `make_cover_thumb`）；`api/routes/books.py`（`handle_cover` 的 `thumb` 参数、FileResponse、etag/304）；`reader/js/shelf.js`（`shelfCoverUrl` / `preloadShelfCovers` / `sceneBookHtml` / 继续阅读封面）；`reader/notes-panel.js`（`coverHtml`）；`scripts/backfill_covers.py`（存量缩略图）；`requirements.txt`（Pillow 可选）。

### 176. SOUL.md 用 `{user}` 指代用户称呼

**结论**：SOUL.md 手稿里写 `{user}` 表示用户自己的称呼，`load_persona` 渲染提示词时按 `settings.json` 的 `user_name` 替换，空名退「用户」。手稿与编辑器始终保留占位符本身，保存不会把人名写死进文件。

- **默认灵魂文稿不写人名**：仓库里的 `SOUL.md` 原来写死固定人名，与身份带里设置的称呼（`user_name`）冲突；现全部改为 `{user}`。
- **替换只发生在读取路径**：`persona.apply_user_name` 是纯函数，`load_persona` 与 `/api/agent` 快照的 `soul_display` 走它；快照里的 `soul` 仍是原始手稿（只归一身份/标题行）。
- **编辑器显示渲染后的文本**：打开「个性化定义」时编辑区按当前称呼/性别替换 `{user}` / `{ta}`，看到的是能直接读的句子；保存时 `mergeSoulEdits` 用逐行 LCS 把**没改过的行**映射回模板，改过/新增的行才落具体文字——占位符不会因为一次保存被写死，增删行也不会让后面的替换整体错位。
- **身份卡摘要本地替换**：`reader/js/theme.js` 的 `soulForDisplay()` 用 `S.userName` 替换 `{user}` 再取首行，改称呼后摘要立即跟随，不等重新拉取 `/api/agent`。
- **记忆提示词去人名**：L2 场景提示词与 scene navigation 示例不再出现具体人名。

**理由**：用户称呼是设置项，不是人格的一部分；写死在灵魂手稿里会让「改称呼」变成一个假的设置项，也会把别人的人名留在默认分发稿里。占位符让手稿保持可读与可编辑，同时保证提示词与界面同源。

**落点**：`SOUL.md`；`persona.py`（`USER_PLACEHOLDER` / `apply_user_name` / `load_persona`）；`api/routes/agent.py`（`_snapshot.soul_display`）；`reader/js/theme.js`（`soulForDisplay` / `renderAgentMeta` / `applyUserName`）；`reader/index.html`（SOUL 编辑器页脚提示）；`memory_pipeline/prompts.py`、`memory_pipeline/scene_store.py`（去掉示例人名）。

### 177. 用户性别与 `{ta}` 占位符

**结论**：设置页「我」那一栏新增性别三档（女 / 男 / 不设置），存 `settings.json` 的 `user_gender`（`female` / `male` / 空）。SOUL.md 与提示词里的第三人称不再写死「他」：手稿用 `{ta}` 占位，性别确认后由 `load_persona` 换成「她 / 他」；未设置时保持中性「ta」。静态提示词模板里的读者代词同样改成「ta」。

- **性别是可选设置**：`GET /api/user` 带 `gender`，`PUT /api/user/gender` 只接受 `female` / `male` / `""`；空值是合法状态，代表「不说明」，不按任何一方猜测。写入走 `update_settings` 增量合并，不动其它字段。
- **占位符只作用于读取路径**：`persona.apply_user_gender` 把 `{ta}` 换成 `他/她/ta`，与 `{user}` 同一条渲染链；`/api/agent` 的 `soul_display` 同时替换两个占位符，`soul` 保留原文；编辑器显示替换后的文本，保存时未改动的行仍映射回 `{ta}`（见 176 的 `mergeSoulEdits`）。
- **三档收进「性别」状态行**：身份卡里只留一行「性别 + 当前值」，点击向下展开选项（grid-template-rows 0fr→1fr 动画 + chevron 旋转）；选中即收起。未设置是正常选项。身份卡不再写「阅读者 · 头像会显示在你的消息旁…」这类说明行。
- **身份卡的摘要在前端替换**：`soulForDisplay()` 按 `S.userName` + `S.userGender` 替换 `{user}` / `{ta}`；改称呼或性别立即重渲染，不用重新拉接口。
- **提示词兜底写进 `## 用户` 段**：性别未设置时明确「第三人称用中性的『ta』，不要猜」；性别已设置时写明「第三人称用『他/她』」，避免模型在 SOUL 之外自行选边。
- **静态模板去性别化**：`prompts/modes/immersive.md` 与 `prompts/archive/thinking_principles.md` 里指代读者的「他」改为「ta」（作者/角色等第三方的「他」不动）。

**理由**：性别与称呼一样是用户的资料，不是人格；写死在灵魂稿里会让模型默认代入一个性别。占位符让手稿保持可读，同时把「确认后才具体化」做成同一条渲染规则：没填就用 neutral，填了就跟随设置。

**落点**：`config.py`（`user_gender` / load / save）；`persona.py`（`GENDERS` / `TA_PLACEHOLDER` / `user_gender` / `user_ta` / `apply_user_gender` / `_user_directive` / `load_persona`）；`api/routes/user.py`（`gender` 字段 + `handle_user_gender_put`）；`api_server.py`（`PUT /api/user/gender`）；`api/routes/agent.py`（`soul_display`）；`reader/index.html`（性别三档）；`reader/style.css`（`.user-gender-*`）；`reader/js/state.js`（`S.userGender`）；`reader/js/theme.js`（`GENDER_TA` / `applyUserGender` / `saveUserGender` / `soulForDisplay`）；`SOUL.md`（8 处用户代词 → `{ta}`）；两个提示词模板（读者代词 → ta）。

### 181. 初次见面引导：按资料缺口注入，拿到答案就收

**结论**：`persona.onboarding_directive(config)` 每轮现算一段「## 初次见面」：只在 `user_name` 为空时注入，邀请 agent 自然地问一次称呼、并允许说「你也可以给我起个名字」；用户给出答案（设置页或 `update_identity` 工具）后下一轮自动消失。注入点只挂在面向用户的对话提示词上（CLI `runtime._build_system_prompt` 与 Web `_build_reading_prompt` 普通模式），不放进 `load_persona` —— 阅读会话、子代理、prompt_budget 复用 persona，但不该问用户名字。新增 `update_identity` 工具让 agent 把对话里得到的称呼 / 性别 / 自己的名字落库。

- **判定边界只有一个：`user_name` 是否为空**。称呼有了整段就不注入；性别不参与判定，也明确要求 agent 不要追问性别（用户自己说起才记）。
- **不靠持久化标志控制骚扰**：注入条件每轮从 config 现算，所以「用户刚在设置页填了名字，提示词还在问」不可能发生；工具改完内存 config，下一轮立刻收摊。
- **克制度写进文案**：只邀请一次；历史里已经问过而用户没接话就不再提；不追问、不成问卷。
- **工具边界**：`update_identity`（DIRECT_MODEL_ONLY，不进子代理）只接受 user_name / user_gender / agent_name 三个可选字段，写 `settings.json` 并同步内存 config；只记「用户真的说出口的」，不负责引导，不为了填满设置去追问。
- **界面跟着工具走**：`tool_end` 收到 `update_identity` 时发 `bc:identity-changed`，主题页重拉 `/api/user` 与 `/api/agent`，身份卡与称呼输入不用等刷新页面。

**理由**：初始化阶段的引导是「资料还没齐」的状态提示，而不是一次性的欢迎语——用状态驱动就天然解决「已经注册还在问」的陈旧注入。把追问性别排除在外，是因为性别是可选资料，追问会变成审问；agent 能给用户起名这件事本身是产品人格的一部分，放在初次见面的自然对话里比放在设置表单里更合适。

**落点**：`persona.py`（`onboarding_directive`）；`runtime.py` / `api/prompt_builders.py`（两处用户对话提示词）；`tools/profile.py`（`update_identity`）；`tools/builtin.py` + `tools/registry.py`（注册与 toolset 标签）；`reader/js/chat.js`（`tool_end` → `bc:identity-changed`）；`reader/js/theme.js`（监听并刷新两份资料）。

### 182. 身份变更的证据日志

**结论**：新增 append-only 表 `identity_events`（sessions.db，迁移 16），记录「哪个会话、什么时候、把哪个字段从什么改成了什么」。写入点两处：`update_identity` 工具（source=agent，带对话 session_id）与设置页 PUT（source=settings，无会话）；每改变一个字段记一行。查询走 `SessionDB.list_identity_events`，agent 侧只读工具 `identity_event_log`（DEFERRED）。

- **会话归属靠 ContextVar**：`identity_log.enter_session/exit_session` 在 `runtime.run_turn`（CLI）与 Web chat 入口设置当前会话；子代理跑完在 finally 里恢复父回合的归属，不会把身份记录错记到子会话。Web 每个请求独立 task，context 天然隔离。
- **只记真实变化**：old == new 不写行；同一字段多次修改是多条记录，保留完整轨迹。
- **证据形状**：`field / old_value / new_value / session_id / source / time_created`；读接口额外带上可读时间与会话标题，回答「什么时候知道的」时不用再拼表。
- **best-effort**：日志写失败只 warning，不影响已经成功的资料保存（与 170/171 的日志纪律一致）。

**理由**：称呼与性别现在既可能来自设置页、也可能来自对话，没有时间与会话就无法回答「这是什么时候、从哪次聊天里知道的」。append-only 与 `annotation_events` / `import_log` 同构，不提供更新删除，才能当证据用。

**落点**：`storage/db_session.py`（迁移 16 `identity_events` + `insert_identity_event` / `list_identity_events`）；`identity_log.py`（ContextVar、`record_changes` / `read_events`）；`tools/profile.py`（工具写日志 + `identity_event_log` 只读工具）；`runtime.py` / `api/routes/chat.py`（会话归属）；`api/routes/user.py`、`api/routes/agent.py`（设置页来源的变更）。
